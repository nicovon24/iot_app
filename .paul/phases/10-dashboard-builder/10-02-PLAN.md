<objective>
## Goal
A real `/dashboard/[id]` page where a user can view a saved custom dashboard's widgets on a `react-grid-layout` grid, toggle "Edit mode" to drag/resize and add widgets one at a time via a short side panel, and save the whole thing in one request to the Phase 10-01 API. The Sidebar's existing `DASHBOARD_OPTIONS` seam becomes real (Main Dashboard + every dashboard from `GET /dashboards`, + "New dashboard").

## Purpose
This is the part the user called "muy importante." 10-01 built the API; this plan makes it usable end-to-end for the simplest case (one dashboard, widgets added one at a time). Bulk-add (10-03) builds on top of the same canvas/save mechanism, not a separate one.

## Output
- `useDashboards()` hooks (list/get/create/save/delete) wired to `GET/POST/PUT/DELETE /dashboards`
- A frontend widget-type registry mirroring the backend's — `widgetType` → component, each fetching its own data via existing hooks and rendering the existing Phase 6/6.4 widget, with an "entity unavailable" fallback when a referenced entity 404s
- `/dashboard/[id]` page: grid render (view mode) + edit mode (drag/resize + add/remove widgets + Save) + one-by-one Add-widget panel
- Sidebar's `DASHBOARD_OPTIONS` populated from `useDashboards()` instead of the hardcoded single-item array, plus a "+ New dashboard" action
</objective>


<task type="auto">
  <name>Task 2: Frontend widget-type registry + DashboardWidgetRenderer</name>
  <files>frontend/src/dashboards/widget-registry.tsx, frontend/src/dashboards/DashboardWidgetRenderer.tsx</files>
  <action>
    `widget-registry.tsx`: exports `WIDGET_REGISTRY: Record<WidgetType, { label: string; needsEntity: boolean; needsTelemetryKey: boolean }>` — one entry per backend widget type (`value-tile`, `line-chart`, `attributes-table`, `alarms-list`, `map`), giving the Add-widget panel (Task 3) enough metadata to know which pickers to show, without duplicating the Zod validation itself (that stays backend-only; this is UI metadata).

    `DashboardWidgetRenderer.tsx`: one component, `<DashboardWidgetRenderer widget={DashboardWidget} />`, `switch (widget.widgetType)` dispatching to 5 small inline sub-components, each:
    - Resolves the entity name/existence first via a local `useEntityRef(entityId, entityType)` (a plain `useQuery` hitting `GET /devices/:id` or `/assets/:id` per `entityType`, mirroring the existing ad-hoc pattern in `app/entities/[id]/page.tsx` — no new shared hook needed for one call site). If it 404s (`ApiError` with `status === 404`), render a shared `<WidgetUnavailable />` inline placeholder (a small bordered box: "Entity unavailable — it may have been deleted") instead of throwing (AC-3).
    - `value-tile`: `useTelemetryLatest(entityId, entityType, [telemetryKey])` → `ValueTileWidget`.
    - `line-chart`: `useTelemetryHistory(entityId, entityType, telemetryKey, { agg, interval })` → `LineChartWidget`.
    - `attributes-table`: `useEntityAttributes(entityId, entityType)` → `AttributesTableWidget`.
    - `alarms-list`: if `entityId` present, `useEntityAlarms`; else `useGlobalAlarms({})` → `AlarmsListWidget`.
    - `map`: if `entityId` present, resolve `latitude`/`longitude` via `useTelemetryLatest` exactly like `entities/[id]/page.tsx` does, then `MapWidget`; else render `FleetMapWidget` as-is (no config needed).
    Avoid: fetching data in the parent grid and passing it down — each widget instance owns its own queries, same as every existing page in this app, so TanStack Query's cache naturally dedupes repeats of the same entity/key across widgets.
  </action>
  <verify>Render a dashboard with one of each widget type against real backend/ThingsBoard data (or a Device with a deliberately fake `entityId` for the unavailable case) and confirm each renders correctly, including the 404 fallback</verify>
  <done>AC-1, AC-3 satisfied</done>
</task>

    `AddWidgetPanel.tsx`: a side panel (reuse `Dialog`'s pattern or a fixed-position glass-card panel, user's choice consistent with existing app style) with, in order: `Select` for widget type (from `WIDGET_REGISTRY`), a `Select` for entity (reusing `useEntities('DEVICE')`/`useEntities('ASSET')` — Device vs Asset choice first if the type needs one), a `Select` for telemetry key (`useTelemetryKeys(entityId, entityType)`, only shown when `WIDGET_REGISTRY[type].needsTelemetryKey`). Renders `<DashboardCanvas>` with the staged widgets. Handle `isError` with `status === 404`/`403` from `useDashboard` by showing a clear "Dashboard not found" / "You don't have access to this dashboard" message instead of a blank page.

    `components/layout/Sidebar.tsx`: replace the hardcoded `DASHBOARD_OPTIONS` constant with a value built inside the component from `useDashboards()`: `[{ label: 'Main Dashboard', href: '/dashboard' }, ...dashboards.map(d => ({ label: d.title, href: '/dashboard/' + d.id }))]`, plus one more entry `{ label: '+ New dashboard', href: '/dashboard/new' }` at the end. `comingSoon` is no longer needed on any dashboard option (drop the field or always `false`) since every option is now real.
