<objective>
## Goal
A second "Add" entry point on the dashboard builder: pick one Device or Asset, see every telemetry key it reports as a checklist, check several, and place all of them on the grid in one "Add N widgets" action — instead of repeating the one-by-one panel's type→entity→key flow per key.

## Purpose
CONTEXT.md's explicit ≤5-minute target for a typical dashboard (~5-8 widgets) isn't reliably reachable through the one-by-one flow alone. Bulk-add is the mechanism that makes it reachable, built on top of 10-02's existing staging/save contract rather than a separate save path.

## Output
- `BulkAddPanel.tsx`: entity picker → telemetry-key checklist → widget-type choice (applies to the whole batch) → "Add N widgets"
- `layout-utils.ts`: a small shared row-packing helper so N new widgets land side by side (wrapping rows) instead of stacked one per row
- `/dashboard/[id]` page gains a second "Bulk add" button opening this panel, alongside the existing one-by-one "Add widget" button from 10-02
</objective>

## AC-1: Bulk-add places one widget per checked key
```gherkin
Given the user opens Bulk add, picks a real Device, and its telemetry keys list includes 4 keys
When the user checks 3 of them and clicks "Add 3 widgets"
Then 3 new widgets are staged on the grid, one per checked key, each a valid value-tile or line-chart config for that key
```

## AC-2: New widgets pack side by side, not stacked one-per-row
```gherkin
Given a dashboard with no existing widgets
When the user bulk-adds 4 value-tile-sized (2x2) widgets in one action
Then they occupy a single row (4 x 2-wide slots fit in a 12-column grid) rather than 4 stacked rows
```

## AC-3: Bulk-add still goes through the same one-request save
```gherkin
Given widgets were added via Bulk add (not yet saved)
When the user clicks Save
Then the exact same PUT /dashboards/:id request fires as after a one-by-one add — no separate bulk-save endpoint
```

  <files>frontend/src/dashboards/layout-utils.ts</files>
  <action>
    Extract and generalize `AddWidgetPanel.tsx`'s single-widget `nextLayout` into a shared `packWidgets(existingLayouts: DashboardWidgetLayout[], newSizes: { w: number; h: number }[], cols = 12): DashboardWidgetLayout[]`. Simple row-packing: start `cursorY` at the max `y+h` of existing layouts, `cursorX` at 0; for each new size, if it doesn't fit before `cols` on the current row, wrap to a new row (`cursorY += rowHeight of the tallest item placed so far in that row`); place left-to-right otherwise. Do not pull in a bin-packing library — this is intentionally simple, matching the "auto-positioned by the grid engine" line from CONTEXT.md (react-grid-layout's own vertical compaction cleans up any imperfection once rendered).
    Update `AddWidgetPanel.tsx` to call `packWidgets(existingLayouts, [meta.defaultLayout])[0]` instead of its inline `nextLayout`, so both panels share one placement rule.

- No per-key widget-type override within one bulk-add batch
