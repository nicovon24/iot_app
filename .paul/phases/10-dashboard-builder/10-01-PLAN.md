<objective>
## Goal
Add the Postgres schema and NestJS `dashboards` module for Phase 10, so a dashboard's title, sharing scope, and full widget list can be created, read (scoped by customer hierarchy + PRIVATE/SHARED visibility), and saved atomically in one request.

## Purpose
This is the foundation every frontend piece (canvas, add-widget panel, bulk-add) depends on. Getting the schema and validation contract right here is what makes the later "AI-readiness" and "sin errores" goals from CONTEXT.md actually true, not just aspirational.

## Output
- 3 new Prisma models (`Dashboard`, `DashboardCustomerAccess`, `DashboardWidget`) + 2 enums, migrated into the real local Postgres instance
- A registry-based widget config validator (5 initial widget types, extensible by adding entries, not editing a switch)
- `dashboards` module: `GET /dashboards`, `GET /dashboards/:id`, `POST /dashboards`, `PUT /dashboards/:id` (atomic whole-dashboard save), `DELETE /dashboards/:id`
</objective>

## AC-3: Visibility and scope enforcement
```gherkin
Given a SHARED dashboard assigned via DashboardCustomerAccess to Customer A (customerScope SPECIFIC)
When a CUSTOMER_USER session whose own customerId is a descendant of Customer A calls GET /dashboards/:id
Then the dashboard is returned
And when a CUSTOMER_USER session from an unrelated Customer calls the same endpoint
Then it is rejected with 403
```

## AC-4: Non-sysadmin cannot create a tenant-wide dashboard
```gherkin
Given an authenticated ADMIN session (not TENANT_ADMIN/SYS_ADMIN)
When POST /dashboards is called with customerScope "ALL"
Then the request is rejected with 403
```

## AC-5: Whole-dashboard save is one transaction
```gherkin
Given an existing dashboard with 2 widgets
When PUT /dashboards/:id is called with a new widget list where the 3rd widget's config is invalid
Then the request is rejected with 400
And the dashboard's widgets in Postgres remain exactly the original 2 (no partial write)
```

<task type="auto">
  <name>Task 2: Widget-type registry + Zod validation</name>
  <files>backend/src/dashboards/widget-registry.ts</files>
  <action>
    Create a registry module, not a switch statement scattered across files. Export:
    - `WIDGET_TYPES` as a const array of the 5 initial keys: `'value-tile' | 'line-chart' | 'attributes-table' | 'alarms-list' | 'map'`
    - A Zod schema per type:
      - `value-tile`: `{ entityId: string (uuid), entityType: 'DEVICE'|'ASSET', telemetryKey: string (min 1) }`
      - `line-chart`: same base + `agg?: 'AVG'|'MIN'|'MAX'|'SUM'|'COUNT'`, `interval?: number (positive int, ms)`
      - `attributes-table`: `{ entityId, entityType }` + `scope?: 'CLIENT_SCOPE'|'SERVER_SCOPE'|'SHARED_SCOPE'`
      - `alarms-list`: `{ entityId?: string (uuid), entityType?: 'DEVICE'|'ASSET' }` — both optional (omitted = customer-scoped global alarms, matching the existing `useGlobalAlarms` pattern)
      - `map`: `{ entityId?: string (uuid), entityType?: 'DEVICE' }` — omitted = fleet map (`FleetMapWidget`), present = single-entity `MapWidget`
    - `validateWidgetConfig(widgetType: string, config: unknown): void` — looks up the schema by `widgetType` (throws `BadRequestException('Unknown widgetType: ...')` if not registered), parses `config` with the matched schema, and on failure throws `BadRequestException` with the Zod error's field path + message (e.g. `"line-chart widget missing required field: telemetryKey"`).
    Adding a 6th widget type later means adding one array entry + one schema here — no other file changes.
    Avoid: a `switch (widgetType)` duplicated in the controller and service — this file is the single place widget-type knowledge lives on the backend.
  </action>
  <verify>Unit-style manual check: call `validateWidgetConfig('line-chart', {})` and confirm it throws naming `entityId`/`entityType`/`telemetryKey`; call it with a valid line-chart config and confirm it returns without throwing</verify>
  <done>AC-2 satisfied: an incomplete config throws before reaching Prisma</done>
</task>

<task type="auto">
  <name>Task 3: DashboardsService + Controller + Module — scoped CRUD, atomic save</name>
  <files>backend/src/dashboards/dto/save-dashboard.dto.ts, backend/src/dashboards/dashboards.service.ts, backend/src/dashboards/dashboards.controller.ts, backend/src/dashboards/dashboards.module.ts, backend/src/common/guards/ws-auth.util.ts, backend/src/app.module.ts</name>
  <action>
    In `ws-auth.util.ts`: export the existing private `isDescendantCustomer` function (add `export` keyword, no behavior change) — `DashboardsService` needs the same ancestor/descendant walk `CustomerScopeGuard` already uses, and the project's own convention (Decisions table) is one shared function, not two implementations of the same rule.

    `save-dashboard.dto.ts`: class-validator DTO for the whole-dashboard save body — `title: string`, `visibility: 'PRIVATE'|'SHARED'`, `customerScope: 'ALL'|'SPECIFIC'`, `customerIds: string[]` (TB customer ids, required non-empty when `visibility=SHARED && customerScope=SPECIFIC`, ignored otherwise), `widgets: { widgetType: string; config: Record<string, unknown>; layout: { x: number; y: number; w: number; h: number } }[]`.

    `dashboards.service.ts`:
    - `list(session)`: returns dashboards where `createdBy === session.tbUserId` (own PRIVATE + own SHARED) OR (`visibility === 'SHARED'` AND visible per scope — see `canView` below) — TENANT_ADMIN/SYS_ADMIN see everything. Use `prisma.dashboard.findMany` with `include: { customerAccess: true }`, then filter the SHARED/SPECIFIC ones in application code via `canView` (small dataset, no need to push the hierarchy walk into SQL).
    - `getById(id, session)`: fetch with widgets + customerAccess; throw `NotFoundException` if missing, `ForbiddenException` if `!canView(dashboard, session)`.
    - `canView(dashboard, session)`: TENANT_ADMIN/SYS_ADMIN → true. `visibility === 'PRIVATE'` → `dashboard.createdBy === session.tbUserId`. `visibility === 'SHARED' && customerScope === 'ALL'` → true. `visibility === 'SHARED' && customerScope === 'SPECIFIC'` → true if any `customerAccess` row has `customerId === session.customerId` OR `isDescendantCustomer(row.customerId, session.customerId, tb)` (session's own customer descends from the assigned one).
    - `create(dto, session)`: if `dto.customerScope === 'ALL'` and caller isn't TENANT_ADMIN/SYS_ADMIN, throw `ForbiddenException`. If caller is a non-sysadmin CUSTOMER_USER, force `customerIds` to `[session.customerId]` regardless of what was passed (can't grant access to another Customer). Validate every widget via `validateWidgetConfig` (Task 2) before any Prisma write. Create `Dashboard` + `DashboardCustomerAccess` rows + `DashboardWidget` rows in one `prisma.$transaction`.
    - `save(id, dto, session)` (used by `PUT /dashboards/:id`): same authorization + validation as `create`, but replaces the dashboard's widgets and customerAccess wholesale inside one `prisma.$transaction` — `deleteMany` then `createMany` for both `DashboardWidget` and `DashboardCustomerAccess`, plus the `Dashboard` row's own field update, all inside the same transaction so a failure anywhere rolls back everything (AC-5). Only the creator or a sysadmin may save.
    - `delete(id, session)`: only creator or sysadmin; Prisma's `onDelete: Cascade` handles widgets/customerAccess.

    `dashboards.controller.ts`: `@Controller('dashboards')`, `@ApiTags('dashboards')`, `@ApiSecurity('session-token')`. `GET /`, `GET /:id` (`ParseTbIdPipe` on `:id` — Dashboard ids are also standard UUIDs), `POST /`, `PUT /:id`, `DELETE /:id` (204). No `@UseGuards(RolesGuard)` needed — `ReaderBlockGuard` (already global) blocks every READER mutation, and the ALL-vs-SPECIFIC sysadmin check lives inside the service since it depends on the request body, not the whole endpoint.

    `dashboards.module.ts`: standard NestJS module wiring `DashboardsController`/`DashboardsService`, importing `PrismaModule`/`ThingsboardModule` (for `isDescendantCustomer`'s `tb` param) the same way `CustomersModule` does.

    Register `DashboardsModule` in `app.module.ts`'s `imports` array (alongside `UsersModule`/`AlarmsModule`) — no guard changes, the three existing global guards already cover session/reader-block; `CustomerScopeGuard` no-ops on these routes (no `?type=` query param) exactly as it does for other non-entity routes today.

    Avoid: reusing `RolesGuard`'s `@Roles('SYSADMIN')` at the controller level for the whole create/save endpoint — that would block a non-sysadmin ADMIN from creating their own SPECIFIC dashboard, which CONTEXT.md explicitly allows.
  </action>
  <verify>`npx tsc --noEmit` clean in `backend/`; manually exercise via Swagger: create a SHARED/SPECIFIC dashboard as a non-sysadmin ADMIN (succeeds, customerIds forced to own customer), attempt `customerScope: "ALL"` as the same user (403), fetch it as a CUSTOMER_USER from an unrelated Customer (403), save an update with one invalid widget (400, original 2 widgets untouched in Postgres)</verify>
  <done>AC-3, AC-4, AC-5 satisfied</done>
</task>
