# Phase Context

**Phase:** 10 — User-editable dashboards (builder)
**Generated:** 2026-08-05 (revised 2026-08-05 — added simplicity/AI-readiness/robustness requirements)
**Status:** Ready for planning (mechanics only — visual styling follows the Phase 9.1 design system)

## Goals

- Admin/sysadmin users can **create custom dashboards**, **edit their layout** (drag/resize widgets on a grid), and **add/remove/configure widgets** on them. This is the part the user explicitly called "muy importante."
- **Radically simpler than ThingsBoard's own dashboard editor** — fewer steps, fewer decisions, no dead ends. ThingsBoard's widget library/datasource/settings flow is the explicit negative reference point: this builder should get a usable widget on the grid in as few clicks as possible, with sane defaults over configuration.
- **Concrete target: a typical dashboard (~5-8 widgets) must be buildable in ≤5 minutes.** One-widget-at-a-time (type → entity → key → Add) doesn't reliably hit this once a dashboard has more than a couple of widgets — the one-by-one flow stays as the precise/single-widget path, but a **bulk-add** path is required as the main lever for the 5-minute target (see Approach).
- **Creation model: canvas-first, not a multi-step wizard.** Creating a dashboard opens a live grid immediately (empty or with a couple of suggested starter widgets); a single lightweight side panel handles "add widget" as one short flow: pick widget type → pick entity/telemetry key → done, no separate steps/screens. No `react-hook-form`-style multi-page wizard for this — that pattern is reserved for the existing Client/Asset creation flows (Phase 7/8), not this one.
- **Leave the door open for AI-assisted dashboard generation later — not built in this phase.** The `Dashboard`/`DashboardWidget` persistence schema and the widget-instance config shape must be clean, self-describing JSON (explicit widget `type` + a flat, typed `config` object per widget — entityId, telemetry key, aggregation, etc.) so that a future agent could plausibly generate or edit that JSON directly without a data-model rework. No generation endpoint, no LLM call, no prompt UI in this phase — purely a modeling discipline applied now to avoid a rewrite later.
- **Leave the door open for dashboard templates ("save as template" / "start from template") — not built in this phase.** No `DashboardTemplate` model or template-picker UI now, but the `Dashboard`/`DashboardWidget` split (a dashboard is just a title + an ordered list of widget configs+layouts) should already be shaped so that "clone this dashboard's widget set into a new one with no customerId/data bound yet" is a plausible later feature, not a redesign. Confirm at planning time whether this only means "don't paint yourself into a corner" or whether a trivial `POST /dashboards/:id/duplicate` (same customer, deep-copies widgets) is cheap enough to include now.
- **Widget system must be extensible beyond the initial 5 types — new types (gauges, additional chart/card variants) are coming in a later phase, not this one.** This phase should NOT hardcode "exactly these 5 widget types" as a closed enum baked into business logic; `widgetType` should be a registry-style mapping (backend: a validated string key + per-type config schema; frontend: a lookup table from `widgetType` → component) so a future phase adds a new widget by registering one new entry, not by touching every dashboard-related file. No gauge widget or new card/chart type is built now.
- **"Sin errores" = the builder must never produce a broken/partial dashboard.** Concretely: widget config is validated before it's addable to the grid (can't drop a chart widget with no entity/key chosen); layout + widget saves are atomic from the frontend's perspective (a failed save doesn't leave some widgets persisted and others not); a dashboard that references a since-deleted entity/device renders a clear "unavailable" placeholder tile instead of crashing the whole page; edit-mode changes are local/uncommitted until an explicit "Save," so a mistake or a closed tab doesn't corrupt the persisted dashboard.
- **Sharing model (revised this session — was "single Customer" only, now more flexible):**
  - Every dashboard has a `visibility`: **`PRIVATE`** (only its creator sees it) or **`SHARED`** (visible to everyone in its assigned Customer scope — see below). No finer ADMIN-vs-READER distinction within `SHARED` — explicitly confirmed this session, consistent with the project's existing stance of deferring per-role/per-area granularity until a real design is chosen (TB CE has no Entity Groups for it).
  - A `SHARED` dashboard's Customer scope is either **`ALL`** (every Customer tenant-wide — **sysadmin-only**, mirrors the existing "All Clients" default view pattern already shipped on `/users`) or **`SPECIFIC`** (one or more individually chosen Customers, each still cascading to its own descendant sub-customers via the existing hierarchy-scoping rule `CustomerScopeGuard` already applies elsewhere). A non-sysadmin `admin` can only create `SPECIFIC` dashboards scoped to their own Customer — they have no tenant-wide "ALL" option.
  - This replaces the earlier "single `customerId` on Dashboard" idea — see the new `DashboardCustomerAccess` join table under Approach.
- The existing fixed **Main Dashboard (Phase 6.5) stays exactly as it is today — non-editable, the system default.** Custom dashboards are additional, reached via a selector/tabs — this is what Phase 6.5's non-functional "future dashboards" seam was anticipating.
- Full persistence of dashboard configs in Postgres: layout (grid position/size per widget) + widget instances + each widget's own config.
- Visual styling of the dashboard builder follows the glassmorphic/purple-accent design system defined in **Phase 9.1** — not a blocker to start the builder's mechanics.

## Approach

- **Grid mechanics:** `react-grid-layout`, per the project's own prior V2 scope note.
- **Creation flow (confirmed this session):** canvas-first. New dashboard → grid view in edit mode by default → floating/side "Add widget" panel: Widget type (from the 5 reused types) → entity picker → telemetry key/attribute picker (only shown if the widget type needs one) → Add. No intermediate confirmation screens. Editing an existing widget reopens the same short panel pre-filled.
- **Bulk-add (new this session, required for the 5-minute target):** pick one or more entities (e.g. a Device or a whole Asset's children) → the panel shows every telemetry key/attribute that entity reports → check the ones to add → each checked key becomes one widget (default widget type per data shape — e.g. a numeric key defaults to `ValueTileWidget`, picking a Line Chart instead is a follow-up edit, not blocking the bulk-add itself) → one "Add N widgets" action places them all on the grid at once, auto-positioned by the grid engine. This is the primary path for populating a dashboard quickly; the one-by-one panel above stays for adding or fine-tuning a single widget.
- **Widgets for v1 — reuse only, 5 initial types, but registered extensibly:** `ValueTileWidget`, `LineChartWidget`, `AttributesTableWidget`, `AlarmsListWidget`, `MapWidget`/`FleetMapWidget` (all exist from Phase 6/6.4). Each becomes "placeable" in a grid item via a `widgetType` registry (not a closed switch/enum scattered across files), wrapped to accept a generic per-instance config loaded from persistence instead of hardcoded page props. New types (gauges, extra chart/card variants) are added later purely by registering a new entry — not built in this phase.
- **New Prisma models** (naming indicative, finalize at planning):
  - `Dashboard` (id, title, createdBy, createdAt, `visibility: PRIVATE | SHARED`, `customerScope: ALL | SPECIFIC` — `ALL` only ever set by a sysadmin-created dashboard). No single `customerId` column — replaced by:
  - `DashboardCustomerAccess` (dashboardId, customerId) — join table, one row per Customer a `SPECIFIC`-scoped dashboard is assigned to (can be more than one). Unused/empty when `customerScope = ALL`. Each row's visibility still cascades to that Customer's descendant sub-customers via the existing hierarchy walk, same rule `CustomerScopeGuard` already applies elsewhere — not reinvented here.
  - `DashboardWidget` (id, dashboardId, widgetType, config JSON, layout `{x,y,w,h}`). `config` JSON shape must be typed per `widgetType` (a discriminated union backend-side, e.g. `LineChartWidgetConfig { entityId, telemetryKey, agg?, interval? }`), not a loose untyped blob — this is the concrete "AI-readiness" requirement: a well-defined, documented schema per widget type.
  - `PRIVATE` dashboards need no `DashboardCustomerAccess` rows at all — visibility is just `createdBy === current user`, checked in `DashboardsService`, no guard changes needed.
- **New backend `dashboards` module:** CRUD scoped through the existing `CustomerScopeGuard` hierarchy logic; create/edit restricted to `ADMIN`/`SYSADMIN`, pairing with Phase 9.2's `ReaderBlockGuard` (`READER` sees shared dashboards read-only, never creates/edits).
- **Validation/robustness, concretely:**
  - Zod (or class-validator DTO) schema per widget type on the backend, rejecting a `DashboardWidget` save whose `config` doesn't match its `widgetType`'s required fields.
  - Frontend "Add widget" panel disables/blocks "Add" until the required fields for the chosen widget type are filled (mirrors backend validation, same pattern as the existing Add Asset flow's client-side blocking).
  - Whole-dashboard save (layout + all widget configs) is one request/transaction, not N independent per-widget saves, so a partial-failure mid-save can't leave the grid inconsistent with the DB.
  - A widget whose `entityId` 404s against ThingsBoard at render time shows an inline "entity no longer available" state instead of an unhandled fetch error crashing the tile or the page.
- **Frontend:** extend the Phase 6.5 dashboard selector seam into a real tab/dropdown switcher (Main Dashboard + each custom dashboard); an "Edit mode" toggle enabling drag/resize + the widget panel described above.

## Constraints

- No new widget types built in this phase — only the 5 existing ones made grid-placeable — but the widget-type mechanism must be a registry, not a hardcoded enum, so gauges/new card/chart types can be added later without touching every dashboard file.
- No dashboard-template model or UI built in this phase — schema shape (dashboard = title + widget list) just needs to not preclude "clone into a template" later.
- No ADMIN-vs-READER distinction within `SHARED` visibility — a `SHARED` dashboard is visible identically to both roles across its assigned Customer scope. Explicitly confirmed this session; do not add role-based dashboard filtering without a fresh discussion.
- No per-individual-user sharing beyond the `PRIVATE`/`SHARED` binary — no "share with these 3 specific users" list in this phase.
- No AI/LLM generation endpoint or prompt UI in this phase — schema-readiness only, confirmed explicitly this session (see Goals).
- Final visual polish follows Phase 9.1's design system; functional builder can be built against current styling first if sequencing requires it.
- Should land after or alongside Phase 9.2 (roles enforcement) ideally — not a hard blocker, both phases are already complete.
- Any map widget placed on a custom dashboard keeps the existing Leaflet styling (map exclusion from 9.1 still applies).

## Open Questions

- Whether a newly created dashboard starts fully blank or with 1-2 suggested starter widgets pre-placed (leaning toward a light starter suggestion per the "simpler than TB" goal, but not decided) — decide at planning time.
- Whether a cheap `POST /dashboards/:id/duplicate` (same-customer deep copy, no template concept needed) is worth including now given how little it adds on top of the registry-based schema, or left fully for a later templates phase — decide at planning time.
- Bulk-add's default widget-type-per-key heuristic (numeric → tile, boolean → ?, etc.) and whether bulk-add supports multiple entities in one pass (e.g. "add these 3 Devices' key temperature reading") or just one entity at a time for v1 — to be nailed down during `/paul:plan`.
