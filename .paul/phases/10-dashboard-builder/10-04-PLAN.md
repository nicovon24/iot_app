<objective>
## Goal
Three configuration capabilities the builder is missing: a **custom title** per widget, a
**click action** per widget (navigate to the clicked entity's detail page), and a **dashboard-wide
time window** that every timeseries widget reads instead of its own hardcoded hour.

## Purpose
Phase 10 shipped a builder that can place widgets but not *configure the presentation* of what
they show. Titles are generated from `entity.name · telemetryKey` with no override, every chart
silently reports the last hour with no way to change or even see that, and the only clickable
thing on a dashboard is a hardcoded "Details" button inside the map popup. The time window in
particular is what makes a dashboard useful for anything historical — without it every chart is
a live-only view.

## Output
- `config.title` and `config.action` accepted by every widget schema (backend Zod + frontend panel)
- `Dashboard.timeWindow` column + a picker in the dashboard header, consumed by line charts
- A shared `widget-actions.ts` seam so future action types (navigate to a dashboard state, open a
  URL) are additive rather than a rework — state navigation itself lands in 10-05
</objective>

<acceptance_criteria>

## AC-1: Custom widget title overrides the generated one
```gherkin
Given a widget whose title currently renders as "industrial-pump-005 · temperature"
When the user sets Title to "Pump 5 — Temp" in the widget config panel and saves the dashboard
Then the widget renders "Pump 5 — Temp" after a page reload
And clearing the Title field restores the generated "industrial-pump-005 · temperature"
```

## AC-2: Widget click action navigates to the entity
```gherkin
Given a widget configured with action "Open entity details"
When the user clicks a row in an Entity Table, a card in Value Cards, or a tile in a Value Tile grid
Then the browser navigates to /entities/{clickedEntityId}?type={entityType}
And a widget configured with action "None" does not navigate on click
```

## AC-3: Dashboard time window drives every timeseries widget
```gherkin
Given a dashboard containing two line-chart widgets
When the user selects "Last 24 hours" in the dashboard header and saves
Then both charts request telemetry over a 24-hour window, not one hour
And reopening the dashboard still shows "Last 24 hours" selected
```

## AC-4: Time window survives an unset value (back-compat)
```gherkin
Given a dashboard row saved before this plan, with timeWindow NULL in Postgres
When the dashboard is opened
Then every timeseries widget falls back to the previous 1-hour behaviour
And no request fails and no console error is raised
```

## AC-5: Invalid config is rejected atomically
```gherkin
Given a save request whose widget carries a title longer than the allowed maximum
When PUT /dashboards/:id is called
Then the API responds 400 naming the offending widgetType and field
And no widget row of that dashboard is modified
```

    Shape (documented in the DTO and mirrored in frontend/src/types/dashboard.ts):
      { kind: 'LAST', ms: number }            // rolling window ending now
      { kind: 'FIXED', startTs: number, endTs: number }
    Validate in SaveDashboardDto with class-validator; reject FIXED where startTs >= endTs.

    Frontend: TimeWindowPicker.tsx — a Select of presets (Last 15 min / 1 hour / 6 hours / 24 hours
    / 7 days) plus a "Custom range" option revealing two datetime inputs. Render it in the
    dashboard header next to the Save/Edit buttons, in BOTH edit and view mode (a viewer must be
    able to change the range without edit rights — changing it in view mode is transient and not
    persisted; only edit mode saves it).

    Plumb it via React context (a `TimeWindowProvider` in the dashboard page) rather than prop-
    drilling through DashboardCanvas — the canvas has no business knowing about time.

    use-widget-datasource.ts: `defaultHistoryWindow()` becomes `resolveHistoryWindow(timeWindow)`
    returning `{startTs, endTs}`, falling back to the current ONE_HOUR_MS behaviour when the
    argument is null/undefined. LineChartCell reads the context value. Keep the existing useMemo
    discipline: the window must be recomputed only when the time window or key changes, never on
    every render — a moving window regenerates the TanStack query key each render and the query
    never settles (this bug is already documented in useTelemetryHistory).

    Avoid: a per-widget time-window override (deferred); polling the window forward on a timer
    (a LAST window recomputes on refetch, not on a tick).
  </action>

## DO NOT CHANGE
- `frontend/src/dashboards/DashboardCanvas.tsx`'s grid configuration — `compactType={null}`,
  `preventCollision`, `draggableCancel`, and the edit-mode `pointer-events-none` rule are all
  deliberate fixes from this session's chat-driven work. Task 2 reads that rule; it must not relax it.
- `frontend/src/lib/chart-palette.ts` — the 8 slots and their order are a validated set; changing
  either breaks colorblind separation.
- The `entityId` / `entityScope` mutual exclusion in the backend `datasource()` refine.
- `react-grid-layout` / `@types/react-grid-layout` versions (pinned, see STATE.md Decisions).

## SCOPE LIMITS
- **No responsive breakpoints and no configurable column count** — explicitly cut by the user.
  `cols={12}` stays hardcoded.
- **No white-labeling / tenant theming** — explicitly cut by the user.
- **No dashboard states/tabs** — that is 10-05. `action: 'NAVIGATE_STATE'` is deliberately NOT in
  the enum yet; adding it without states to point at would be a dead option.
- **No reusable entity aliases** — that is 10-06.
- No per-widget time-window override; the window is dashboard-wide only.
- No unit/decimals dictionary (explicitly cut by the user).
