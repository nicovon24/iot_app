<objective>
## Goal
An operator can read alarms for a specific entity or across their whole customer hierarchy via REST, and subscribe to live alarm push over WebSocket — closing the last item in PROJECT.md's core value ("live... alarms for any entity... without ThingsBoard credentials ever reaching the browser") and completing Phase 3.

## Purpose
Alarms are the other live-data half of Phase 3 (telemetry was 03-01). ThingsBoard's Rule Engine remains the sole source of alarm truth (PROJECT.md: "Replacing ThingsBoard's Rule Engine" is out of scope) — this plan only reads and relays, never creates/acks/clears alarms (no such endpoints exist yet; V1 scope per ROADMAP is read-only).

## Output
- `AlarmsService`/`AlarmsController`: `GET /entities/:id/alarms` (per-entity, reuses the existing `CustomerScopeGuard` `:id`+`type` scoping automatically), `GET /alarms` (global, customer-hierarchy scoped like `EntitiesService.list`)
- `AlarmsGateway` (`/ws/alarms`): same client-facing subscribe/unsubscribe protocol as `TelemetryGateway`, same auth/scope reuse
- `ThingsboardWsService` extended with an alarm-subscription method on the same multiplexed upstream connection (no second upstream socket)
</objective>

<acceptance_criteria>

## AC-1: Per-entity alarms are readable and scoped
```gherkin
Given an authenticated session (TENANT_ADMIN or a CUSTOMER_USER in scope for entity X)
When it calls GET /entities/X/alarms?type=DEVICE
Then it receives X's real ThingsBoard alarms (paginated); a CUSTOMER_USER out of scope for X gets 403 via the existing CustomerScopeGuard
```

## AC-2: Global alarm list is customer-hierarchy scoped
```gherkin
Given a CUSTOMER_USER session scoped to customer A (plus descendants)
When it calls GET /alarms
Then it receives only alarms belonging to devices/assets owned by customer A or its descendants — never another customer's alarms; a TENANT_ADMIN/SYS_ADMIN session gets alarms across the whole tenant
```

## AC-3: Global alarm list supports severity/status filtering
```gherkin
Given any authenticated session
When it calls GET /alarms?severity=CRITICAL&status=ACTIVE
Then only alarms matching that severity and status are returned
```

## AC-4: Live alarm push over WebSocket, scoped like telemetry
```gherkin
Given an authenticated session subscribes over /ws/alarms to an in-scope entity
When ThingsBoard raises or updates an alarm for that entity
Then the client receives an `{event:"alarm", ...}` frame; an out-of-scope subscribe attempt gets a forbidden error frame and no alarm data, matching TelemetryGateway's AC-1/AC-2 behavior from 03-01
```
