<objective>
## Goal
A client can open a WebSocket connection to the backend, subscribe to live telemetry for a given entity (respecting the same customer-hierarchy scoping as the REST API), and receive updates as ThingsBoard pushes them — without ever holding a ThingsBoard token.

## Purpose
Closes the last gap in PROJECT.md's core value ("view live... telemetry... without ThingsBoard credentials ever reaching the browser") — REST covers historical/latest reads (Phase 2/2.1), this plan adds the live path.

## Output
- `ThingsboardWsService`: maintains one upstream WS connection to ThingsBoard's telemetry API per active subscription, with reconnect/backoff
- `TelemetryGateway`: Nest WS gateway (`@nestjs/platform-ws` adapter) — client-facing subscribe/unsubscribe protocol, authenticated and customer-scoped per connection
- `main.ts` wired with `WsAdapter`
</objective>

<acceptance_criteria>

## AC-1: Connection requires a valid session
```gherkin
Given a client opens a WS connection to /ws/telemetry without a valid session token
When the connection handshake completes
Then the server closes the connection immediately with an error code/reason, no subscription is accepted
```

## AC-2: Subscribing to an out-of-scope entity is rejected
```gherkin
Given an authenticated CUSTOMER_USER session scoped to customer A
When that client sends a subscribe message for a DEVICE owned by customer B (not a descendant of A)
Then the server replies with an error frame for that subscription and does not relay any telemetry for it
```

## AC-3: Subscribing to an in-scope entity streams live updates
```gherkin
Given an authenticated session in scope for entity X (TENANT_ADMIN, or CUSTOMER_USER owning/ancestor of X)
When that client sends a subscribe message for entity X's telemetry
Then the server establishes (or reuses) an upstream ThingsBoard WS subscription for X and relays each telemetry update to the client as it arrives
```

## AC-4: Unsubscribe and disconnect clean up upstream state
```gherkin
Given a client is subscribed to entity X
When the client sends an unsubscribe message, or disconnects
Then the backend stops relaying updates to that client, and tears down the upstream ThingsBoard subscription for X once no client backend-wide still needs it
```

## AC-5: Upstream reconnects on drop
```gherkin
Given the backend's upstream WS connection to ThingsBoard drops unexpectedly
When the drop is detected
Then the backend reconnects with backoff and re-establishes all currently-active entity subscriptions, without requiring clients to reconnect
```

</acceptance_criteria>

<task type="auto">
  <name>Task 1: Wire WsAdapter + WS session/scope authentication util</name>
  <files>backend/src/main.ts, backend/src/common/guards/ws-auth.util.ts</files>
  <action>
    In `main.ts`, after creating the Fastify Nest app, call `app.useWebSocketAdapter(new WsAdapter(app))` (from `@nestjs/platform-ws`) so `@WebSocketGateway()` decorators work over the existing HTTP server via the `ws` library — no separate port, no Fastify-plugin route.

    Create `ws-auth.util.ts` exporting a function `resolveWsSession(sessionToken: string, authService: AuthService): Promise<AppSession>` that reuses `AuthService.getSession()` (same Redis-backed session lookup `SessionAuthGuard` already uses for REST) — do not duplicate session-parsing logic, import and call the existing method.

    Also export `isEntityInScope(session: AppSession, entityId: string, entityType: EntityType, entitiesService: EntitiesService, tb: ThingsboardClientService): Promise<boolean>` — extract the exact scoping decision `CustomerScopeGuard.canActivate` already makes (TENANT_ADMIN/SYS_ADMIN bypass; else compare `getOwningCustomerId` against `session.customerId` or its descendants via `isDescendantCustomer`) into this shared, reusable function. Refactor `CustomerScopeGuard` to call this same function internally instead of duplicating the logic — the REST guard and the WS gateway must use one scoping decision, not two copies that can drift.

    The client sends its session token as a WS handshake query param (`?token=<sessionToken>`) since WS handshakes have no custom-header support in browsers; read it via `req.url` query parsing in `handleConnection`.
  </action>
  <verify>`npx tsc --noEmit` passes; `CustomerScopeGuard`'s existing behavior is unchanged (same scoping decisions, just delegating to the extracted function) — no regression in REST `:id`-scoped routes</verify>
  <done>AC-1 satisfied: groundwork for connection-time auth exists and is reused, not duplicated, from the REST auth/scoping path</done>
</task>

<task type="auto">
  <name>Task 2: ThingsBoard upstream WS telemetry client with reconnect/backoff</name>
  <files>backend/src/thingsboard/thingsboard-ws.service.ts, backend/src/thingsboard/thingsboard.module.ts</files>
  <action>
    Create `ThingsboardWsService`, injectable, added to `ThingsboardModule`'s providers/exports (same module that already owns `ThingsboardClientService`/`RedisService` — this is the third TB-facing chokepoint, WS instead of REST).

    On first subscription request, open a single upstream `ws` connection to `wss://{host}/api/ws/plugins/telemetry?token={serviceAccountToken}` (reuse `ThingsboardClientService.getToken()` for the token — same service-account credential already used for REST, per the existing "shared credential" model documented in STATE.md; do not invent a new credential path here). Multiplex all entity subscriptions over this one upstream connection using ThingsBoard's own `cmdId`-keyed protocol: send `{"tsSubCmds":[{"entityType":..., "entityId":..., "scope":"LATEST_TELEMETRY", "cmdId": N}], "historyCmds":[], "attrSubCmds":[]}` per entity, tracking `cmdId -> entityId` so incoming `{"subscriptionId": N, "data": {...}}` frames can be routed back to the right entity.

    Expose:
    - `subscribe(entityType, entityId, onUpdate: (data) => void): () => void` — returns an unsubscribe function; increments a per-entity ref count so the same entity subscribed by 2 clients only opens 1 upstream `tsSubCmd`, and only sends the corresponding unsubscribe cmd when the ref count hits 0.
    - Reconnect: on `close`/`error` from the upstream socket, retry with exponential backoff (mirror the pattern already used in `RedisService`'s `retryStrategy` — same project convention for transient-connection resilience). On reconnect, resend `tsSubCmds` for every entity with an active ref count > 0 (rebuild subscriptions, since ThingsBoard's WS has no server-side session persistence across a dropped socket).
    Avoid: opening one upstream connection per client — ThingsBoard connection limits make that unnecessary and wasteful; the multiplexing is the point of this service.
  </action>
  <verify>Manual: with a real ThingsBoard Cloud device that has active telemetry, call `subscribe()` twice for the same entity from a small script, confirm only one upstream `tsSubCmds` frame is sent (log it) and both callbacks fire on each update; kill network briefly and confirm reconnect + resubscribe happens without the test script re-calling `subscribe()`</verify>
  <done>AC-3 and AC-5 satisfied: upstream multiplexed subscription delivers live updates and survives a dropped connection</done>
</task>

<task type="auto">
  <name>Task 3: TelemetryGateway — client-facing subscribe protocol</name>
  <files>backend/src/telemetry/telemetry.gateway.ts, backend/src/telemetry/telemetry.module.ts</files>
  <action>
    Create `TelemetryGateway` (`@WebSocketGateway({ path: '/ws/telemetry' })`), implementing `OnGatewayConnection`/`OnGatewayDisconnect`.

    `handleConnection(client)`: parse `token` from the connection URL query string, resolve the session via `resolveWsSession` (Task 1). If missing/invalid, call `client.close()` immediately (AC-1) — do not accept any messages first.

    Message handler `subscribe` (`@SubscribeMessage('subscribe')`), payload `{ entityId, entityType }`: check `isEntityInScope` (Task 1) using the connection's resolved session; if out of scope, send back `{ event: 'error', entityId, message: 'forbidden' }` on that socket and do not call `ThingsboardWsService.subscribe` (AC-2). If in scope, call `ThingsboardWsService.subscribe(entityType, entityId, (data) => client.send(...))`, store the returned unsubscribe function keyed by `(client, entityId)` in an in-memory map on the gateway instance (AC-3).

    Message handler `unsubscribe`, same payload shape: look up and call the stored unsubscribe function, remove it from the map (AC-4, explicit unsubscribe path).

    `handleDisconnect(client)`: call every stored unsubscribe function for that client and clear its map entries (AC-4, disconnect path) — this is what actually decrements `ThingsboardWsService`'s ref counts when a client drops without unsubscribing first.

    Register `TelemetryGateway` and `ThingsboardWsService`-consuming wiring in `telemetry.module.ts`.
  </action>
  <verify>Manual with `wscat`: connect with a valid token to `/ws/telemetry`, send a subscribe message for an in-scope entity, observe live update frames; send subscribe for an out-of-scope entity (as a CUSTOMER_USER), observe the forbidden error frame and no data frames for it; disconnect and confirm (via Task 2's logging) the upstream unsubscribe fires</verify>
  <done>AC-1 through AC-4 fully satisfied end-to-end against real ThingsBoard Cloud</done>
</task>
