<objective>
## Goal
Runtime-verify Phase 2.2-01/2.2-02 against real ThingsBoard, close the list-endpoint customer-scoping gap, and confirm (or fix) the relation type `CustomerScopeGuard` assumes for sub-customer hierarchy — so Phase 2.2 can actually be marked done and `/paul:unify` run.

## Purpose
Phase 2.2 shipped two plans "code complete" but STATE.md logs three unresolved gaps that mean the security model it claims (customer-hierarchy scoping) isn't actually enforced end-to-end: it was never run against real TB, list endpoints leak cross-customer data, and the hierarchy relation type is an unverified guess. Closing these is what makes the phase's stated goal ("real per-user identity and authorization") true rather than aspirational.

## Output
- Confirmed (or corrected) sub-customer relation type in `CustomerScopeGuard`
- List endpoints (`GET /devices`, `GET /assets`, `GET /entities`, `GET /customers`) filtered by caller's customer + descendants for `CUSTOMER_USER` sessions
- AC-0 through AC-4 from `2.2-01-PLAN.md` confirmed against a live TB Tenant Admin + Customer User (with a real sub-customer relation)
- List endpoints support real pagination (`page`, `pageSize`, or "all"), `textSearch`, `sortProperty`, `sortOrder`, matching ThingsBoard's own `PageData` contract
- `entities`/`devices`/`assets` responses expose `tenantId`, `customerId`, `assetProfileId`, `ownerId`, `additionalInfo`
</objective>

## AC-1: Sub-customer relation type is confirmed against real ThingsBoard
```gherkin
Given a Tenant Admin account in the real TB instance and two customers where one is meant to be a sub-customer of the other
When the relation between them is created and inspected via ThingsBoard's relations API
Then `CustomerScopeGuard`'s assumed relation type ("Contains", direction FROM parent TO child) either matches what TB actually returns, or the guard code is corrected to match the real type/direction
```

## AC-2: List endpoints are scoped by customer hierarchy for Customer Users
```gherkin
Given a logged-in `admin`/`reader` Customer User scoped to customer A, where customer A has a descendant sub-customer B with its own devices
When they call GET /devices, GET /assets, GET /entities?type=DEVICE, and GET /customers
Then results only include entities/customers belonging to customer A or its descendants (B included), never entities from unrelated customers
```

## AC-3: sysadmin list endpoints remain unscoped
```gherkin
Given a logged-in sysadmin (TB Tenant Admin) session
When they call the same list endpoints
Then results are unfiltered (full tenant visibility, matching current behavior)
```

## AC-4: Phase 2.2-01 AC-0 through AC-4 pass against real ThingsBoard
```gherkin
Given a real TB Tenant Admin login and a real Customer User (admin or reader role) with a sub-customer relation set up per AC-1
When each AC-0..AC-4 scenario from 2.2-01-PLAN.md is exercised manually via Swagger/curl
Then all pass as originally specified, and any deviation is fixed before this plan is marked done
```

## AC-5: List endpoints support pagination/textSearch/sort matching TB's PageData contract
```gherkin
Given GET /devices, GET /assets, GET /entities, GET /customers
When called with page/pageSize query params
Then results are paginated accordingly; omitting them (or an explicit "all" option) returns the full scoped result set
And textSearch filters by name, sortProperty/sortOrder controls ordering, mirroring ThingsBoard's own PageData response shape
```

## AC-6: Extra fields exposed on entities/devices/assets
```gherkin
Given any GET /entities, GET /devices, GET /assets response (list or :id)
When the response is inspected
Then it includes tenantId, customerId, assetProfileId (assets only), ownerId, and additionalInfo alongside existing fields
```
