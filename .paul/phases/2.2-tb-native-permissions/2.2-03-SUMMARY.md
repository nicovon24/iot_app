# 2.2-03 Summary

## Outcome
All 6 acceptance criteria (AC-1 through AC-6) verified against real ThingsBoard Cloud (PE trial). Phase 2.2 is now truly done, not just code-complete.

## What shipped
- **AC-1 (relation-type fix):** Confirmed ThingsBoard PE exposes a native `parentCustomerId` field on Customer entities (not available in CE) plus a dedicated `POST /api/owner/CUSTOMER/{ownerId}/{entityType}/{entityId}` API to set it. `CustomerScopeGuard.isDescendantCustomer` rewritten to walk `parentCustomerId` upward instead of generic `Contains` relations. Verified live: created a real parent/child customer pair via the owner API and confirmed the guard correctly resolves it.
- **AC-2/AC-3 (list scoping):** `EntitiesService.list()` now branches on session authority — `TENANT_ADMIN`/`SYS_ADMIN` get unscoped tenant-wide results (forwarded to TB's own paginated endpoints), `CUSTOMER_USER` sessions get results aggregated across their own customer + all resolved descendant customers (via `/api/customer/{id}/devices|assets` and an in-memory customer filter).
- **AC-5 (pagination):** New `PaginationQueryDto` (`page`, `pageSize`, `textSearch`, `sortProperty`, `sortOrder`) added to `devices`, `assets`, `customers`, `entities` list endpoints, forwarded to TB's native `PageData` contract for unscoped sessions; applied client-side for scoped (multi-customer-aggregated) sessions.
- **AC-6 (field exposure):** `EntityRef`/`TbDevice`/`TbAsset`/`TbCustomer` extended with `tenantId`, `customerId`, `assetProfileId` (assets only), `ownerId`, `additionalInfo`. Verified present on both list and `:id` responses.
- **AC-4 (full runtime verification):** Logged in as both a real TB Tenant Admin and a real Customer User (`operator@customer-a.com`, activated via TB's own activation-link flow to set a test password). Confirmed: in-scope `:id` access (200), out-of-scope `:id` access (clean 403, not a leaked TB 404), scoped list (1 device, the correct one), unscoped sysadmin list (full tenant), and no-token access (401).

## Real bug found and fixed (not part of the original plan, found during verification)
`SessionAuthGuard` and `CustomerScopeGuard` were registered as `APP_GUARD` in two different modules (`AuthModule` and `AppModule` respectively). Nest's execution order across `APP_GUARD` providers registered in different modules is not guaranteed by declaration order across modules — in practice `CustomerScopeGuard` ran **before** `SessionAuthGuard`, so `request.session` was always `undefined` at the point `CustomerScopeGuard` checked it, causing it to silently take the "no session, defer" bypass path for every `:id`-scoped request, every time — Phase 2.2's per-entity scoping was never actually enforced, on any request, since it shipped. List-endpoint scoping (added in this plan) happened to still work because it reads the session at controller/handler execution time, by which point both guards have already run regardless of their relative order.

**Fix:** both guards now registered in `AppModule`'s own `providers` array, in explicit order (`SessionAuthGuard` first, `CustomerScopeGuard` second) — Nest guarantees same-array declaration order. `AuthModule` no longer registers a guard, only `AuthService`.

Also fixed along the way: `isDescendantCustomer` now catches a 404 while walking `parentCustomerId` (e.g. hitting TB's `NULL_UUID` placeholder customer on an unassigned entity) and treats it as "not a descendant" (403) instead of leaking TB's raw 404 error to the caller.
