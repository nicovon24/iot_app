<objective>
## Goal
Replace the shared-TB-account login with real ThingsBoard authentication, and scope every request to the caller's place in ThingsBoard's own customer hierarchy: a `sysadmin` (Tenant Admin) sees everything; an `admin`/`reader` (Customer User) sees its own customer plus any descendant sub-customers, nothing else.

## Purpose
Phase 2.1 shipped a global `SessionAuthGuard`, but it only answers "is this session valid?" — every valid session carries the same privilege, because login checks credentials against one configured TB account (`config.thingsboardUsername`/`Password`) shared by the whole app. A code review after Phase 2.1 found two concrete exploits of this (CR-01: unvalidated `:id` path params allow path traversal to arbitrary TB endpoints using the shared privileged credential; CR-02: unescaped `keys` query params allow query injection) and the deeper issue: there is no way to say "this user only sees customer X." This plan fixes both — the input-validation holes and the missing authorization layer — because the second is meaningless without the first (an attacker who can path-traverse past validated ids also walks around any hierarchy check built on top).

## Output
- `auth/`: login authenticates against real ThingsBoard (`POST /api/auth/login`) instead of a shared config credential; session in Redis carries `{ tbUserId, authority, customerId }`
- `CustomerScopeGuard`: new guard, applied alongside `SessionAuthGuard`, that resolves the target entity's owning customer and checks it against the caller's `customerId` + its descendant sub-customers (bypassed entirely for `TENANT_ADMIN`)
- `:id` path params validated as TB UUIDs before use in any outbound TB request (closes CR-01)
- `URLSearchParams` used consistently for all query params built from user input (closes CR-02)
- New `users` module: `sysadmin`-only CRUD for `admin`/`reader` Customer Users, backed by TB's own user API — no parallel app-owned users table
</objective>

<acceptance_criteria>

## AC-0: Login authenticates against real ThingsBoard, not a shared config credential
```gherkin
Given a ThingsBoard Tenant Admin account and a ThingsBoard Customer User account both exist
When each logs in via POST /auth/login with their own TB credentials
Then both succeed, each session in Redis stores that user's own tbUserId/authority/customerId — not the same values for both

Given invalid TB credentials
When POST /auth/login is called
Then ThingsBoard's own rejection is surfaced as 401, no fallback to any shared/config account
```

## AC-1: `:id` params are validated before reaching any ThingsBoard request (CR-01)
```gherkin
Given a request to any entity-scoped endpoint (e.g. GET /devices/:id, GET /entities/:id/attributes)
When :id is not a well-formed ThingsBoard UUID (e.g. contains "/", "..", or other path characters)
Then the backend responds 400 before any outbound call to ThingsBoard is made
```

## AC-2: Query params built from user input never allow injection (CR-02)
```gherkin
Given GET /entities/:id/attributes?keys=foo&bar=baz (a key value containing "&")
When the backend builds the outbound ThingsBoard request
Then "bar=baz" is never interpreted as a separate query parameter — URLSearchParams encodes the whole value safely
```

## AC-3: Customer-hierarchy scoping — sysadmin sees all, customer user sees own + descendants only
```gherkin
Given customer A has a sub-customer A1, and an unrelated customer B exists
And an admin/reader user is attached to customer A
When that user requests an entity owned by A or by A1
Then the request succeeds

When that user requests an entity owned by B
Then the backend responds 403, without the request ever reaching ThingsBoard with the shared/service credential

Given a sysadmin (Tenant Admin) session
When it requests any entity regardless of owning customer
Then the request succeeds — no hierarchy check applied
```

## AC-4: Users module — sysadmin-only, TB-native, sysadmin account is undeletable
```gherkin
Given a sysadmin session
When it calls POST /users with { email, password, role: 'ADMIN'|'READER', customerId }
Then a real ThingsBoard Customer User is created under that customerId, visible via ThingsBoard's own user API

Given an admin or reader session (not sysadmin)
When it calls POST /users or DELETE /users/:id
Then the backend responds 403

Given a sysadmin session
When it calls DELETE /users/:id targeting the tenant admin account itself
Then the backend responds 400/403 and the account is not deleted
```
