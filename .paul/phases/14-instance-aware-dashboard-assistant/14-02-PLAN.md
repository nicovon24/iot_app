<objective>
## Goal
A signed-in user can converse with their configured model to create a dashboard or revise an existing one through a validated draft without saving it automatically. First-release provider settings include OpenAI, Anthropic, Gemini, Groq, OpenRouter, and an administrator-approved custom API URL.

## Purpose

The uncommitted AI code already stores an encrypted user key and produces one JSON draft. A chatbot needs turns, revision context, explicit errors, and durable isolation.

## Output

Conversation and message persistence, provider adapters, a draft-generation endpoint, and focused backend tests.
</objective>

<acceptance_criteria>

## AC-1: Private provider settings

Given multiple configured provider/model/key connections for one app user and ThingsBoard instance, when another user or instance reads settings, then the keys and connections are inaccessible. Each key can be replaced or removed independently; responses never return it.

## AC-2: Multi-turn draft

Given a catalog of supported widgets, visible devices, and their telemetry keys and an existing conversation, when the user creates a dashboard or opens an existing one and requests a revision, the assistant returns a new structured draft based on the current layout and request. Only authorized device IDs, telemetry keys, and supported widgets enter the draft.

## AC-3: Safe persistence

Given an AI response with invalid widget configuration, out-of-scope entity, or provider error, the endpoint returns a clear error without saving a dashboard or leaking a key. A valid draft is saved only through the existing dashboard save flow after user review.

## AC-4: Edit permissions

Given a READER session, when the user calls AI settings, conversation, generation, or dashboard-save endpoints, then the backend denies the operation. Only roles with dashboard edit permission can use the assistant.

## AC-5: User limits

Given a user's configured daily request limit and maximum response tokens, when the user sends a prompt, then the backend applies both limits before calling the provider and reports the remaining daily requests. A request denied by the limit does not call the provider.
</acceptance_criteria>

<boundaries>
## DO NOT CHANGE
- ThingsBoard owns telemetry and entity records; provider output cannot create them.
- Existing saved dashboards and widget configs remain valid until the user explicitly saves a reviewed revision.

## SCOPE LIMITS

- No automatic dashboard publishing, current or historical telemetry values sent to model providers, or autonomous device actions. Custom provider URLs must be on the administrator-approved HTTPS origin list.
- Streaming can be deferred until the bounded nonstreaming conversation works; the UI must still show pending state.
</boundaries>
