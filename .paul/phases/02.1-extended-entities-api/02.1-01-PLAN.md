<objective>
## Goal
Extend Phase 2's read-only, single-entity-type API into: (1) real interval-bucketed aggregation for timeseries (e.g. avg temperature every 5 minutes) with an unbounded-by-default result set, (2) attribute reads filtered by key and attribute writes (POST/PUT), (3) Device/Asset creation, (4) Customer as a third entity type alongside Device/Asset.

## Purpose
Phase 2 only covered read paths for Device/Asset, and — gap discovered while extending it — never actually enforced the app session it issues: `/auth/login` returned a `sessionToken`, but every other endpoint (entities, devices, assets, attributes, telemetry) was reachable with no session at all. This plan closes that (session required from here on, everywhere, including Swagger's own "Try it out") and adds the first write paths into ThingsBoard (creating devices/assets, writing attributes) plus real bucketed aggregation — both needed before Phase 6 (frontend dashboards) can show "avg temperature every 5 min" charts, and before V2's onboarding wizards have anything to build on.

## Output
- Global `SessionAuthGuard` protecting every controller except `POST /auth/login`; Swagger configured with a bearer/apiKey security scheme so its "Authorize" button covers all documented endpoints in one step
- `telemetry/timeseries` fixed to expose `limit` (default: unset — TB's own unlimited/default behavior, not the previous bug that collapsed the whole range into one bucket) and `interval` (ms) + `agg` for real bucketed aggregation
- `attributes` GET gains `keys` filter; new POST endpoint to write attributes
- `devices`, `assets` gain POST create endpoints
- `entities` supports `CUSTOMER` as a third `EntityType`
- New `customers` module (list, get by id) mirroring `devices`/`assets`
</objective>

<acceptance_criteria>

## AC-0: Every endpoint requires a valid session, Swagger included
```gherkin
Given no `x-session-token` header (or an invalid/expired one)
When a client calls any endpoint other than POST /auth/login
Then the backend returns 401, before the request reaches entities/devices/attributes/telemetry logic

Given a client opens Swagger UI at /api/docs and clicks "Authorize", entering a session token obtained from POST /auth/login
When they then use "Try it out" on any other endpoint
Then the session token is sent automatically and the request succeeds — no manual header copying per request
```

## AC-1: Timeseries without an artificial limit, real interval aggregation
```gherkin
Given a client calls GET /entities/:id/telemetry/timeseries?keys=temperature&startTs=X&endTs=Y (no limit, no agg)
When the range spans more raw points than ThingsBoard's own default page size
Then the backend does not truncate further than ThingsBoard itself does — no hardcoded default limit is added by this API

Given a client calls the same endpoint with agg=AVG&interval=300000 (5 minutes)
When ThingsBoard returns bucketed averages
Then the response contains one averaged temperature value per 5-minute bucket across the range, not a single value for the whole range (fixes the Phase 2 bug where interval was silently set to the full range)
```

## AC-2: Attributes — key filter and writes
```gherkin
Given an entity has 10 SERVER_SCOPE attributes
When a client calls GET /entities/:id/attributes?type=DEVICE&scope=SERVER_SCOPE&keys=active,lastConnectTime
Then only those 2 keys are returned, not all 10

Given a client calls POST /entities/:id/attributes?type=DEVICE&scope=SERVER_SCOPE with body { "customLabel": "Pump A" }
When the request succeeds
Then a subsequent GET for that key returns the new value, and any cached Redis entry for that entity/scope is invalidated (not served stale)
```

## AC-3: Device/Asset creation
```gherkin
Given a client calls POST /devices with { name, type } (or POST /assets with { name, type })
When the request succeeds
Then ThingsBoard has a new device/asset, and the response is an EntityRef with its real TB-assigned id
```

## AC-4: Customers as a first-class entity type
```gherkin
Given ThingsBoard has Customers under the tenant
When a client calls GET /entities?type=CUSTOMER or GET /customers
Then customers are returned normalized to EntityRef, same shape as devices/assets
```

<task type="auto">
  <name>Task 1: Fix timeseries — unbounded default, real interval-bucketed aggregation, explicit limit</name>
  <files>backend/src/telemetry/telemetry.service.ts, backend/src/telemetry/telemetry.controller.ts</files>
  <action>
    - Remove the current bug: `interval` was being set to `endTs - startTs` whenever `agg` was passed, which collapses the whole range into a single bucket instead of aggregating per window.
    - `getTimeseries(entityId, entityType, keys, startTs, endTs, options?: { agg?: string; intervalMs?: number; limit?: number })`:
      - No `agg`/`interval`: forward `startTs`/`endTs`/`keys` to TB as-is, plus `limit` only if the caller explicitly passed one (omit the param entirely otherwise — do not invent a default, let TB apply its own default so "no value = see everything TB gives")
      - `agg` + `intervalMs` present: forward `agg`, `interval=intervalMs` to TB's timeseries endpoint — this produces one bucketed value per `intervalMs` window (e.g. `interval=300000` = 5 minutes), per ThingsBoard's own aggregation API contract
      - `agg` without `intervalMs`: reject with a 400 (`BadRequestException`) — aggregation requires a bucket size, don't silently guess one
    - Controller: `@ApiQuery` for `limit` (optional, number, no default documented as "omit for ThingsBoard's own default/unlimited"), `interval` (optional, ms, required together with `agg`), keep `agg` enum as-is
    Avoid: reintroducing any backend-side default for `limit` — the whole point of this fix is "no value = all values."
  </action>
  <verify>GET .../timeseries?keys=temperature&startTs=X&endTs=Y&agg=AVG&interval=300000 over a 1-hour range returns ~12 distinct averaged points, not 1</verify>
  <done>AC-1 satisfied</done>
</task>
