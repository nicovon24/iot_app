<objective>
## Goal
A real login screen at `/login` authenticates against the backend's `POST /auth/login` (which itself authenticates against real ThingsBoard credentials per Phase 2.2), persists the resulting session token across page refreshes, redirects unauthenticated users to `/login` from anywhere else in the app, and provides a working logout.

## Purpose
This is the last piece of Phase 5's foundation — every future page (Phase 6 entity views, Phase 7 wizard) needs a real logged-in session to call the already-built `apiClient`/`ws-client` (05-02) with a valid token. Without this plan, `getSessionToken()` is permanently `null` and every API call 401s.

## Output
- `frontend/src/lib/session.ts` extended with `sessionStorage` persistence (survives refresh, cleared on tab close — appropriate for this PoC, no "remember me" long-lived cookie needed)
- `frontend/src/lib/auth.ts`: `login(username, password)` and `logout()` functions calling the real backend endpoints and updating session state
- `frontend/src/app/login/page.tsx`: a real login form (HeroUI `Input`/`Button`), themed to match the dark-navy/electric-blue shell, shows a real error message on 401
- `frontend/src/components/AuthGate.tsx`: client-side redirect-to-`/login` for any route when no session token exists (UX convenience, not a security boundary — the real enforcement is the backend's `SessionAuthGuard` on every API call)
- Logout affordance added to the Sidebar (or a small user-menu area)
</objective>

```gherkin
Given the login form at /login
```

```gherkin
Given a user is logged in (token persisted in sessionStorage)

Then getSessionToken() still returns the persisted token and the user is NOT redirected to /login
```

## AC-4: Unauthenticated access to any protected route redirects to /login
```gherkin
Given no session token is set
When the user navigates to /dashboard, /devices, /assets, or /alarms
Then AuthGate redirects to /login before any protected content renders
```

## AC-5: Logout clears the session and calls the real backend
```gherkin
Given a logged-in user
When they trigger logout
Then POST /auth/logout is called with the real token, sessionStorage is cleared, getSessionToken() returns null, and the user is redirected to /login
```

<task type="auto">
  <name>Task 1: Session persistence + auth actions</name>
  <files>frontend/src/lib/session.ts, frontend/src/lib/auth.ts</files>
  <action>
    Update `session.ts`: back the in-memory variable with `sessionStorage` (guard all access with `typeof window !== 'undefined'` since this module is imported by both client and server components/layouts). On `setSessionToken(token)`, write to `sessionStorage.setItem('iot_session_token', token)` (or `removeItem` if `token` is `null`). Add `initSessionFromStorage()` that reads `sessionStorage` once (called once from a client component near the app root, e.g. `AuthGate`, not from every render) to hydrate the in-memory variable on load — `sessionStorage` alone isn't enough since `getSessionToken()` is a synchronous in-memory read used by `api-client.ts`/`ws-client.ts`.
    Create `auth.ts` exporting `async function login(username: string, password: string): Promise<void>` — calls `apiClient.post<{sessionToken: string}>('/auth/login', {username, password})`, then `setSessionToken(result.sessionToken)` on success; let `ApiError` propagate (the login page catches it for the error message, don't swallow it here). Export `async function logout(): Promise<void>` — calls `apiClient.post('/auth/logout')` (already sends the current token via the existing header wiring), then `setSessionToken(null)` regardless of whether the backend call succeeds (a failed logout call shouldn't leave the user stuck logged in client-side).
    Avoid: any password/credential storage beyond the single fetch call — never persist the password, only the resulting session token.
  </action>
  <verify>
    With the backend running, call `login()` with real credentials from a temporary script (or the login page built in Task 2) — confirm `getSessionToken()` returns the real token and `sessionStorage.getItem('iot_session_token')` matches. Refresh a loaded page and confirm `initSessionFromStorage()` restores the token. Call `logout()` and confirm both the real `POST /auth/logout` fires and the token is cleared.
  </verify>
  <done>AC-3, AC-5 (backend-call and persistence halves) satisfied</done>
</task>

<task type="auto">
  <name>Task 2: Login page</name>
  <files>frontend/src/app/login/page.tsx</files>
  <action>
    Create a `'use client'` login page at `/login`: HeroUI `Input` (username, password type="password") + `Button` (type="submit"), styled consistent with the app's dark-navy/electric-blue theme (e.g. a centered card on `bg-surface`, using the existing `surface-card`/`accent` tokens — do not hardcode new colors). On submit, call `login(username, password)` from Task 1's `auth.ts`; on success, `router.push('/dashboard')` (Next.js `useRouter`); on failure, catch `ApiError` and display its message (e.g. "Invalid username or password" for a 401, or the raw backend message otherwise) in a visible error state near the form — do not silently fail.
    This page does NOT render inside the app shell's protected area — since `AppLayout` (Task 3) will apply `AuthGate` at the root layout level, `/login` itself must be exempted from the redirect check (see Task 3's exemption list), and this page's own layout should NOT include the `Sidebar`/gradient header (a logged-out user shouldn't see the full app chrome) — render a minimal centered layout local to this page instead.
    Avoid: client-side "remember me" / long-lived token storage — `sessionStorage` (Task 1) is the deliberate choice for this PoC.
  </action>
  <verify>
    Load `/login` in a browser (or via `curl`/fetched HTML) — confirm it renders without the Sidebar/header. Submit real valid credentials — confirm redirect to `/dashboard`. Submit invalid credentials — confirm a visible error message renders and the URL stays `/login`.
  </verify>
  <done>AC-1, AC-2 satisfied</done>
</task>

<task type="auto">
  <name>Task 3: AuthGate route protection + logout affordance</name>
  <files>frontend/src/components/AuthGate.tsx, frontend/src/app/providers.tsx, frontend/src/components/AppLayout.tsx, frontend/src/components/Sidebar.tsx</files>
  <action>
    Create `AuthGate.tsx`: a `'use client'` component that calls `initSessionFromStorage()` once on mount (via `useEffect`), then checks `getSessionToken()`. If null and the current pathname (via `usePathname()`) is not `/login`, `router.push('/login')` and render nothing (or a minimal loading state) until the redirect completes; otherwise render `{children}`. This is a client-side UX redirect only — real enforcement stays server-side via the backend's `SessionAuthGuard` on every API call, so a determined user bypassing this check still gets real 401s from `apiClient`, they just wouldn't see a nice `/login` redirect.
    Wire `AuthGate` into `Providers` (wrapping `AppLayout`, so it's applied once at the root) OR directly into `AppLayout` — pick whichever keeps `/login`'s page (Task 2, which renders its own minimal layout, not `AppLayout`) outside the gate; since `/login` doesn't use `AppLayout`, wiring `AuthGate` inside `AppLayout` itself (not `Providers`) is simpler and correctly scopes the check to only the protected shell.
    Add a logout affordance to `Sidebar.tsx`: a small button/icon at the bottom of the icon rail (e.g. a `LogOut` lucide icon in a `Tooltip`) that calls `logout()` from `lib/auth.ts` then `router.push('/login')`.
    Avoid: adding this check to `middleware.ts` or any server-side mechanism — the token lives in `sessionStorage` (browser-only), so this must be a client component check, not middleware (which runs before the browser's storage is accessible).
  </action>
  <verify>
    With no session token set, navigate directly to `/dashboard`, `/devices`, `/assets`, `/alarms` — confirm each redirects to `/login` before rendering protected content. Log in, confirm access to all four routes works. Click the Sidebar's logout button — confirm `sessionStorage` is cleared and the browser lands on `/login`.
  </verify>
