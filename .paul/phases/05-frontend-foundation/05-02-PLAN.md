<objective>
## Goal
`frontend/` gains a typed data layer: a REST API client (`lib/api-client.ts`) that talks to the real NestJS backend with the session-token header the backend's `SessionAuthGuard` expects, a WS client factory (`lib/ws-client.ts`) for the telemetry/alarms gateways, shared TypeScript types mirroring the backend's own type contracts, and a TanStack Query provider wired into the app shell.

## Purpose
Phase 6 (entity views) and Phase 7 (client wizard) both need a working way to call the backend — this plan is the one place that logic lives, so no page/hook duplicates fetch/auth logic later.

## Output
- `frontend/src/types/` — `EntityRef`/`EntityRefLink`/`EntityType`, `TelemetryValue`/`TelemetryLatest` (values always `string`, never `number`, per `.paul/rules/api.md`), `AttributesPayload`, `Alarm`/`AlarmSeverity`/`AlarmStatus`, `PageData<T>` — named to mirror `backend/src/types/*.ts` 1:1 in shape
- `frontend/src/lib/session.ts` — minimal in-memory session-token getter/setter (no login UI yet, that's 05-03; just the storage seam both clients read from)
- `frontend/src/lib/api-client.ts` — typed `fetch` wrapper sending `x-session-token`, throwing on non-2xx with the backend's real error body attached
- `frontend/src/lib/ws-client.ts` — factory connecting to `/ws/telemetry` or `/ws/alarms` with `?token=` query param (browsers can't set custom WS handshake headers — matches the backend's own documented protocol), typed subscribe/unsubscribe/message handling
- `frontend/src/lib/query-client.ts` + `Providers` update — TanStack Query wired into the existing `HeroUIProvider` wrapper
</objective>

  <files>frontend/package.json, frontend/src/lib/session.ts, frontend/src/lib/api-client.ts, frontend/src/lib/query-client.ts, frontend/src/app/providers.tsx</files>
  <action>
    Install `@tanstack/react-query` into the frontend workspace (`npm install @tanstack/react-query --workspace=frontend` — run from repo root per this session's established convention, never `cd frontend && npm install`, to avoid a conflicting nested `node_modules`).
    Create `lib/session.ts`: a minimal module-level seam — `let sessionToken: string | null = null; export function getSessionToken() { return sessionToken; } export function setSessionToken(token: string | null) { sessionToken = token; }`. This is intentionally thin; 05-03's login screen will call `setSessionToken` after a real `POST /auth/login` — do not build a Zustand store or persistence layer here, that's 05-03's call to make once the login UX is designed.
    Create `lib/api-client.ts`: reads `NEXT_PUBLIC_API_BASE_URL` (default `http://localhost:3001` if unset — matches the backend's Phase 1 default port) from `process.env`. Export `class ApiError extends Error { status: number; body: unknown }` and an `apiClient` object with typed `get<T>(path: string): Promise<T>` / `post<T>(path: string, body?: unknown): Promise<T>` methods. Every call sets `x-session-token` from `getSessionToken()` (omit the header entirely if null, matching how `SessionAuthGuard` treats a missing token) and `Content-Type: application/json` on POST. On a non-2xx response, parse the JSON error body (backend errors are always JSON per NestJS's default exception filter) and throw `new ApiError(response.statusText, response.status, body)` — do not swallow the real status/body, callers need them to distinguish 401 vs 403 vs 400.
    Create `lib/query-client.ts`: exports a singleton `queryClient = new QueryClient()` with a short `staleTime` (e.g. 5000ms, matching the backend's own short telemetry cache TTL) as sane defaults — don't over-configure retry/refetch behavior here, defaults are fine for this plan's scope.
    Update `app/providers.tsx`: wrap the existing `HeroUIProvider` with `QueryClientProvider client={queryClient}`, keeping `Providers` as the single client-boundary component (no new provider file).
    Avoid: hardcoding `localhost:3001` anywhere except as the `NEXT_PUBLIC_API_BASE_URL` fallback — every other call site must go through `apiClient`, never construct its own `fetch` call, mirroring the backend's own `ThingsboardClientService.request()` single-chokepoint pattern.
