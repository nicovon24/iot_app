<objective>
## Goal
Give the frontend everything it needs to build the admin hierarchy panel: expose `parentCustomerId` for sub-client breadcrumbs, a way to read the real Contains-relation tree (Customer/Asset → child Assets/Devices), an Asset update endpoint, and Device assign/unassign endpoints — all without duplicating ThingsBoard state in Postgres.

## Purpose
The admin panel (08-02) needs to browse the real TB hierarchy (sub-customers, nested Assets, linked Devices) and edit/link/unlink from it. None of these read/write capabilities existed before this phase — Phase 4.3 deliberately left Device linking and relation-reads out of V1 scope. This phase closes exactly those gaps, reusing the existing Relations API pattern from `EntitiesService.createRelation` (Phase 4.3).

## Output
- `EntityRef.parentCustomerId` (CUSTOMER only), resolved/cached the same way as other ref fields
- `EntitiesService.getRelationChildren(fromId, fromType)` — real Contains-relation children, split into `{assets, devices}`
- `EntitiesService.updateAsset()`, `deleteRelation()`, widened `createRelation()` (now allows `toType: 'DEVICE'`)
- `PATCH /assets/:id`, `GET /assets/:id/children`, `POST /assets/:id/devices`, `DELETE /assets/:id/devices/:deviceId`, `GET /customers/:id/children`
- `AssetsService.delete()` now blocks if the Asset has children (Assets or Devices) — same integrity guard as `CustomersService.delete()`
</objective>

<acceptance_criteria>

## AC-1: Sub-customer breadcrumbs are resolvable
```gherkin
Given a Customer created with a parentCustomerId (sub-customer)
When GET /customers is called
Then that Customer's EntityRef includes a resolved parentCustomerId {id, name}, not a bare id
```

## AC-2: Contains-relation children are readable, split by type
```gherkin
Given a Customer with a level-0 Asset attached via Contains, and that Asset has a child Asset and a linked Device
When GET /customers/:id/children is called for the Customer, and GET /assets/:id/children for the Asset
Then the Customer's response lists the level-0 Asset under `assets` (empty `devices`), and the Asset's response lists its child Asset under `assets` and the linked Device under `devices`
```

## AC-3: A Device can be assigned to and unassigned from an Asset
```gherkin
Given a real Asset and a real Device both exist
When POST /assets/:id/devices {deviceId} is called, then GET /assets/:id/children
Then the Device appears in the `devices` array
When DELETE /assets/:id/devices/:deviceId is called, then GET /assets/:id/children again
Then the Device no longer appears
```

## AC-4: An Asset's name/type/label can be updated
```gherkin
Given a real Asset exists
When PATCH /assets/:id {name: "New Name"} is called
Then GET /assets/:id reflects the new name, with type/label unchanged
```

## AC-5: Asset deletion is blocked when it has children
```gherkin
Given an Asset has a linked Device (or a child Asset)
When DELETE /assets/:id is attempted
Then it returns 400 with a message naming how many child Assets/Devices remain, and the Asset is not deleted
```
