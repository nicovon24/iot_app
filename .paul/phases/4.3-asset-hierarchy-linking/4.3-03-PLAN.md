<objective>
## Goal
`POST /assets` stops creating bare, unlinked Assets. Every Asset created through this endpoint must now specify which Customer's hierarchy it belongs to, which level of that hierarchy it represents, and a parent (the Customer itself, or an existing Asset) to attach to via a real ThingsBoard "Contains" relation.

## Purpose
This is the first real step of building the nested Customer→Asset tree that Phase 4 deliberately deferred to V2 (see STATE.md Deferred Issues: "Real nested Customer→Asset→Device entity tree"). The user has now decided to pull Asset-level linking into V1, while Device creation is removed entirely in the same phase (4.3-02) rather than extended the same way.

## Output
- New Prisma model `AssetHierarchyAssignment` (customerId, assetId, levelIndex) — the only place this backend tracks "what hierarchy level is this Asset," since ThingsBoard has no such concept natively
- `CreateAssetDto` requires `customerId`, `levelIndex`, and `parentId` (Customer id or Asset id)
- A new `AssetsService` validates the level against the Customer's real `CustomerHierarchyLevels`, validates the parent, creates the Asset in ThingsBoard, records the assignment in Postgres, and creates a real TB "Contains" relation from the parent to the new Asset
- `EntitiesService` gains a `createRelation` helper (first real use of ThingsBoard's Relations API in this codebase — see STATE.md's existing "Contains relations remain in use elsewhere" comment in `CustomerScopeGuard`, which until now was purely aspirational)
</objective>

## AC-1: Asset created at the first hierarchy level, parented to the Customer
```gherkin
Given a Customer "Test Comp" with hierarchy levels [Site(0), Area(1), Asset(2), Sensor(3)]
When POST /assets is called with { name: "Plant North", type: "site", customerId: "<Acme id>", levelIndex: 0, parentId: "<Acme id>" }
Then a real ThingsBoard Asset is created, an AssetHierarchyAssignment row exists (customerId=Acme, levelIndex=0), and a real TB "Contains" relation exists from Acme (CUSTOMER) to the new Asset
```

## AC-2: Asset created at a deeper level, parented to an existing Asset
```gherkin
Given the Asset "Plant North" from AC-1 (level 0)
When POST /assets is called with { name: "North Wing", type: "area", customerId: "<Acme id>", levelIndex: 1, parentId: "<Plant North's id>" }
Then a real ThingsBoard Asset is created, an AssetHierarchyAssignment row exists (levelIndex=1), and a real TB "Contains" relation exists from "Plant North" (ASSET) to "North Wing"
```

## AC-3: Invalid levelIndex is rejected
```gherkin
Given the Customer "Test Comp" has only 4 levels (indices 0-3)
When POST /assets is called with levelIndex: 9 for that customerId
Then the request is rejected with 400, no Asset is created in ThingsBoard, no rows written to Postgres
```

## AC-4: Non-existent parentId is rejected
```gherkin
Given a parentId that is neither the given customerId nor an existing Asset
When POST /assets is called
Then the request is rejected with 404 (or 400), no Asset is created in ThingsBoard, no rows written to Postgres
```

## AC-5: Rollback on partial failure
```gherkin
Given a valid request that passes DTO validation and level/parent checks
When the ThingsBoard Asset is created successfully but the Postgres AssetHierarchyAssignment write fails
Then the just-created ThingsBoard Asset is deleted (compensating action), matching the pattern already established in CustomersService.create
```

<task type="auto">
  <name>Task 1: AssetHierarchyAssignment Prisma model + migration</name>
  <files>backend/prisma/schema.prisma, backend/prisma/migrations/</files>
  <action>
    Add to `backend/prisma/schema.prisma`:
    ```prisma
    model AssetHierarchyAssignment {
      id         String @id @default(uuid())
      customerId String
      assetId    String @unique
      levelIndex Int
    }
    ```
    `assetId` is `@unique` because each real TB Asset can only be assigned to one hierarchy position — this is a 1:1 mapping from TB Asset id to its level, not a many-to-many. Add an index on `customerId` implicitly via a `@@index([customerId])` since lookups will filter by customer when validating parent/level consistency.
    Run `npx prisma migrate dev --name asset_hierarchy_assignment` against the real `iot-postgres` container (port 15432, see STATE.md Decisions) — do NOT use `migrate reset` this time, this is an additive migration on top of the existing `CustomerHierarchyLevels` table, no destructive schema change needed.
    Avoid: adding a foreign key to `CustomerHierarchyLevels` — that table is keyed by `(customerId, levelIndex)` composite, not a single id, and the two tables don't need a DB-level FK for this to work; a plain `customerId`/`levelIndex` pair validated in application code (Task 2) is sufficient and simpler.
  </action>
  <verify>`npx prisma migrate status` shows the new migration applied; `docker exec iot-postgres psql -U postgres -d iot_app -c '\dt'` lists `AssetHierarchyAssignment` alongside the existing `CustomerHierarchyLevels`</verify>
  <done>Schema foundation for AC-1/AC-2 (assignment persistence) in place</done>
</task>

<task type="auto">
  <name>Task 2: AssetsService — validation, TB Asset creation, Postgres assignment, rollback</name>
  <files>backend/src/assets/dto/create-asset.dto.ts, backend/src/assets/assets.service.ts, backend/src/entities/entities.service.ts</files>
  <action>
    Rewrite `CreateAssetDto`: keep `name`/`type`/`label`, add required `customerId: string` (`@IsString @IsNotEmpty`), `levelIndex: number` (`@IsInt @Min(0)`), `parentId: string` (`@IsString @IsNotEmpty` — either the Customer's own id or an existing Asset's id).
    Add `EntitiesService.createRelation(fromId: string, fromType: 'CUSTOMER' | 'ASSET', toId: string, toType: 'ASSET'): Promise<void>` that calls `this.tb.request('POST', '/api/relation', { from: { id: fromId, entityType: fromType }, to: { id: toId, entityType: toType }, type: 'Contains', typeGroup: 'COMMON' })` — this is the first real use of TB's Relations API in this codebase (previously only referenced conceptually in `CustomerScopeGuard`'s comments).
    Create `AssetsService` (new file) with `create(dto: CreateAssetDto)`:
    1. Validate `levelIndex` exists for `dto.customerId` — query `prisma.customerHierarchyLevels.findUnique({ where: { customerId_levelIndex: { customerId: dto.customerId, levelIndex: dto.levelIndex } } })` (Prisma auto-generates this compound-unique accessor from the existing `@@unique([customerId, levelIndex])`); if null, throw `BadRequestException`.
    2. Resolve parent: if `dto.parentId === dto.customerId`, the parent is the Customer itself — require `dto.levelIndex === 0` (first level attaches directly to the Customer), else throw `BadRequestException`. Otherwise, look up `prisma.assetHierarchyAssignment.findUnique({ where: { assetId: dto.parentId } })`; if not found, throw `NotFoundException` (parent Asset isn't a tracked hierarchy member); if found, require it belongs to the same `customerId` and its `levelIndex` is exactly `dto.levelIndex - 1` (parent must be the immediately preceding level), else throw `BadRequestException`.
    3. Create the Asset in ThingsBoard via `entitiesService.createAsset(dto.name, dto.type, dto.label)`.
    4. Write `prisma.assetHierarchyAssignment.create({ data: { customerId: dto.customerId, assetId: created.id, levelIndex: dto.levelIndex } })`. On failure, call `entitiesService.deleteAsset(created.id)` (add this small method to `EntitiesService`, mirroring `deleteCustomer`) and rethrow — same compensating-rollback pattern as `CustomersService.create`.
    5. Create the TB relation: `entitiesService.createRelation(dto.parentId, dto.parentId === dto.customerId ? 'CUSTOMER' : 'ASSET', created.id, 'ASSET')`.
    6. Return the created Asset (`EntityRef`).
    Avoid: trusting the client-supplied parent/level pairing without the lookups above — the whole point of this plan is that the hierarchy is enforced, not just recorded.
  </action>
  <verify>
    Directly exercise `AssetsService.create` via the controller (see Task 3) against real ThingsBoard + Postgres:
    valid level-0 request succeeds and both a `CustomerHierarchyLevels` match and an `AssetHierarchyAssignment` row exist;
    `levelIndex: 9` on a 4-level Customer returns 400;
    a `parentId` that is neither the Customer nor a tracked Asset returns 404;
    a level-1 Asset whose `parentId` is a level-0 Asset from a DIFFERENT customer returns 400.
  </verify>
  <done>AC-1, AC-2, AC-3, AC-4 satisfied</done>
