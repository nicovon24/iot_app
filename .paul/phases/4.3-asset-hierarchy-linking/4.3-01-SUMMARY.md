# Phase 4.3 Plan 01: parentCustomerId on Customer creation Summary

**`POST /customers` now accepts an optional `parentCustomerId`, creating the new Customer as a sub-customer of an existing one in a single atomic request.**

## Acceptance Criteria Results

| Criterion | Status | Notes |
|-----------|--------|-------|
| AC-1: Customer created with a parent | Pass | Verified live against real ThingsBoard Cloud — created "Sub A" under "Test", confirmed `parentCustomerId.id` via `GET /customers/:id` |
| AC-2: Customer without parent still works | Pass | Relies on the unchanged prior-verified root-creation path; not re-run fresh this session (quota-blocked), but code path unchanged from Phase 4 |
| AC-3: Invalid parentCustomerId rejected | Pass | Malformed (non-string) value rejected with 400 before reaching ThingsBoard |

## Files Created/Modified

| File | Change | Purpose |
|------|--------|---------|
| `backend/src/customers/dto/create-customer.dto.ts` | Modified | Added optional `parentCustomerId: string` field |
| `backend/src/customers/customers.service.ts` | Modified | Forwards `dto.parentCustomerId` to `EntitiesService.createCustomer` |
| `backend/src/entities/entities.service.ts` | Modified | `createCustomer` signature gained optional `parentCustomerId`, wired into the TB request body as `{id, entityType: 'CUSTOMER'}` |

## Decisions Made

| Decision | Rationale | Impact |
|----------|-----------|--------|
| No strict TB-id validation on `parentCustomerId` | Mirrors `CreateUserDto.customerId`'s existing pattern; ThingsBoard enforces real existence on write | Simpler DTO, consistent validation style across the codebase |

## Deviations from Plan

None — followed plan as specified.

**Ready:** Sub-customer creation is live and usable by the Phase 7 wizard later.
**Concerns:** AC-2 relies on a prior-verified code path rather than a fresh live re-check this session (TB Cloud trial Customer quota was the blocker).
**Blockers:** None.
