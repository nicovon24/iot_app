<objective>
## Goal
`EntityRef`'s reference fields (`tenantId`, `customerId`, `assetProfileId`, `ownerId`) stop being bare TB id strings and become `{id, name, label}` objects, so a frontend can display a customer/tenant/profile name without a second round-trip per reference.

## Purpose
Requested improvement (`.paul/IMPROVEMENTS.md` — "EntityRef Reference Fields") ahead of Phase 5's frontend needing to render these without N+1 lookups per list row.

## Output
- `EntityRefLink` type: `{ id: string; name?: string; label?: string }`
- `EntitiesService` batch-resolves all four reference kinds for an entire list response in as few TB calls as possible, deduped by unique id, cached in Redis with a longer TTL than the existing telemetry/attribute cache (these change rarely)
- `EntityRef.tenantId`/`customerId`/`assetProfileId`/`ownerId` typed as `EntityRefLink | undefined` instead of `string | undefined`
</objective>

  <name>Task 2: Batched, cached reference resolution in EntitiesService</name>

  <action>
    Add a private method `resolveRefs(refs: {id: string; kind: 'tenant'|'customer'|'assetProfile'|'owner'}[]): Promise&lt;Map&lt;string, EntityRefLink&gt;&gt;` that:
    - Dedupes by `id` first (a list of 50 devices from the same customer should resolve that customer's name exactly once)
    - Checks Redis first per id (cache key e.g. `refname:{kind}:{id}`, TTL ~300s — long-lived since names change rarely, distinct from the existing ~3s telemetry cache TTL; add this constant near `RedisService` usage, do not reuse the telemetry cache's short TTL)
    - For cache misses: batch by kind and resolve via the minimal number of TB calls — customers can be resolved from the already-fetched `/api/customers` page (reuse the same call `resolveScopedCustomerIds` already makes when scoping is active; for unscoped/global calls, fetch `/api/customers?pageSize=1000` once and build an id→{name,label:undefined} map from it, since `TbCustomer` has no `label` field). Tenant: fetch via `GET /api/tenant/{id}` once per unique tenantId (in this project's single-tenant model, this will only ever resolve once and can then be cached long-term). Asset profile: fetch via `GET /api/assetProfile/{id}` (confirm this exact path against real ThingsBoard Cloud before finalizing — TB's asset/device profile REST paths should mirror the device profile pattern, but this hasn't been used anywhere in the codebase yet, so treat it as needing empirical confirmation, same practice used for `tsSubCmds` in Phase 3). Owner: `ownerId.entityType` tells you whether to resolve it as a tenant or customer — reuse the same resolution as those two kinds, keyed by `entityType`.
    - Writes newly-resolved entries back to Redis with the long TTL
    - On any individual resolution failure (e.g. a stale/deleted reference id), log a warning and leave that entry out of the returned map rather than failing the whole batch — `toEntityRef` should degrade to `{id}` with no `name`/`label` for that one reference, not break the whole response

    Update `toEntityRef` (or make it async / move the ref-building into `list`/`getById` after fetching raw entities) to build the flat list of `{id, kind}` refs needed across the whole batch of entities being mapped, call `resolveRefs` once, then build each `EntityRef` from the resolved map — do not call `resolveRefs` once per entity (that reintroduces the N+1 this plan exists to remove).

    Update `list`, `listUnscoped`, and `getById` accordingly (they currently call the synchronous `toEntityRef` per-entity — restructure to fetch raw entities first, batch-resolve refs, then map).
  </action>
