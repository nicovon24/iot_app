<objective>
## Goal
A sysadmin can create a Client with its full hierarchy-level list in a single atomic request, and later fetch that hierarchy — with no way to edit it afterward, matching PROJECT.md's "hierarchy is static after creation" constraint.

## Purpose
This is V1's only wizard (per PROJECT.md/ROADMAP.md) and the one piece of app-owned persistence in the whole system. Genuine dependency on 04-01: this plan imports `PrismaService` and the `Client`/`ClientHierarchyLevels` models 04-01 creates.

## Output
- `POST /clients` — creates a `Client` row + its ordered `ClientHierarchyLevels` rows in one Prisma transaction
- `GET /clients/:id/hierarchy` — returns the Client's hierarchy levels in order
- Swagger docs for both, including an explicit note that hierarchy is immutable after creation
</objective>

<acceptance_criteria>

## AC-1: Client + hierarchy created atomically
```gherkin
Given a sysadmin session and a valid payload { name: "Acme", hierarchyLevels: [{levelIndex: 0, name: "Region"}, {levelIndex: 1, name: "Plant"}] }
When POST /clients is called
Then a Client row and both ClientHierarchyLevels rows exist in Postgres, created in a single transaction (verified: if one insert were to fail, none would persist)
```

## AC-2: Empty hierarchy is rejected
```gherkin
Given a payload with hierarchyLevels: []
When POST /clients is called
Then the request is rejected with 400, no Client row is created
```

## AC-3: Non-sysadmin cannot create a Client
```gherkin
Given an authenticated session with authority other than sysadmin (TENANT_ADMIN/SYS_ADMIN)
When POST /clients is called
Then the request is rejected with 403, mirroring the existing RolesGuard/@Roles('SYSADMIN') pattern from users.controller.ts
```

## AC-4: Hierarchy is readable and ordered
```gherkin
Given a Client created via AC-1
When GET /clients/:id/hierarchy is called
Then it returns the hierarchy levels ordered by levelIndex ascending
```

## AC-5: No update/edit endpoint exists
```gherkin
Given the ClientsController
When inspected
Then it exposes only POST /clients and GET /clients/:id/hierarchy — no PATCH/PUT for hierarchy, matching PROJECT.md's "immutable after creation" constraint
```
