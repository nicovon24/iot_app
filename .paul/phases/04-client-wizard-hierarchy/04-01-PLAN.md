<objective>
## Goal
Stand up Postgres (local Docker) + Prisma in the backend, with a migrated schema for `Client` and `ClientHierarchyLevels` — the only two tables Postgres owns in V1, per PROJECT.md's narrow persistence scope.

## Purpose
Phase 4's wizard (04-02) needs somewhere to atomically persist a Client and its ordered hierarchy levels. ThingsBoard has no concept of "Client" or arbitrary hierarchy depth, so this is genuinely new persistence, not a duplicate of TB data (see PROJECT.md Technical Context: "Postgres is reserved for metadata ThingsBoard doesn't model").

## Output
- Postgres running locally via Docker (same pattern as the existing `iot-redis` container)
- `@prisma/client` + `prisma` installed, `backend/prisma/schema.prisma` with `Client` and `ClientHierarchyLevels` models
- A applied migration creating both tables
- `PrismaModule`/`PrismaService` (global module, one shared client instance) ready for 04-02 to inject
</objective>

<task type="auto">
  <name>Task 2: Prisma schema, migration, and PrismaModule/PrismaService</name>
  <files>backend/prisma/schema.prisma, backend/prisma/migrations/, backend/src/prisma/prisma.module.ts, backend/src/prisma/prisma.service.ts, backend/src/app.module.ts, backend/package.json</files>
  <action>
    Install `prisma` (dev dep) and `@prisma/client` (dep) in `backend/`. Run `npx prisma init` only if `prisma/` doesn't already exist, then replace the generated schema with:
    - `datasource db`: postgresql, `url = env("DATABASE_URL")`
    - `generator client`: `prisma-client-js`
    - `model Client { id String @id @default(uuid()); name String; createdAt DateTime @default(now()); hierarchyLevels ClientHierarchyLevels[] }`
    - `model ClientHierarchyLevels { id String @id @default(uuid()); clientId String; client Client @relation(fields: [clientId], references: [id]); levelIndex Int; name String; @@unique([clientId, levelIndex]) }`
    (`levelIndex` gives 04-02 an explicit, uniquely-constrained ordering — avoids relying on array/insertion order for something that must be immutable and orderable.)
    Run `npx prisma migrate dev --name init_client_hierarchy` against the real `iot-postgres` container (not a mock/sqlite substitute — this project verifies against real infra per STATE.md conventions).
    Create `PrismaService` (`backend/src/prisma/prisma.service.ts`) extending `PrismaClient`, implementing `OnModuleInit`/`OnModuleDestroy` (connect/disconnect), following the same lifecycle-hook shape as `RedisService`'s `OnModuleDestroy`.
    Create `PrismaModule` (`@Global()`, exports `PrismaService`) and register it in `AppModule`'s imports — global so 04-02's `clients` module doesn't need to re-import it.
    Avoid: instantiating `PrismaClient` anywhere except inside `PrismaService`.
  </action>
  <verify>`npx prisma migrate status` (from `backend/`) shows the migration applied with no pending migrations; `docker exec iot-postgres psql -U postgres -d iot_app -c '\dt'` lists both `Client` and `ClientHierarchyLevels` tables</verify>
  <done>AC-2, AC-3, AC-4 satisfied: schema matches scope, migration applied against real Postgres, PrismaService injectable</done>
