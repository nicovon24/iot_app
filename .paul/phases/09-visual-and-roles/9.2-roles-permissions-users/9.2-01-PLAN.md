<objective>
## Goal
`appRole: 'READER'` currently has no enforcement anywhere except `@Roles('SYSADMIN')`-gated endpoints — any authenticated READER can write/edit/delete like an ADMIN today. Add a new global guard that blocks every mutating HTTP method (POST/PUT/PATCH/DELETE) whenever the session's `appRole` is `'READER'`, with zero exceptions inside their own scope.

## Purpose
Closes a real authorization gap identified while scoping Phase 9.2: `READER` is stored on TB Customer Users (`additionalInfo.appRole`) at creation but never checked. The user confirmed explicitly: "solo mirar y punto, no debe poder cambiar nada." `ADMIN` and `SYSADMIN` behavior must stay exactly as today — this plan only tightens `READER`.

## Output
A new `ReaderBlockGuard` registered as a third global `APP_GUARD` (after `SessionAuthGuard`, `CustomerScopeGuard`), throwing 403 on any mutating request from a READER session.
</objective>

<acceptance_criteria>

## AC-1: READER is blocked from every mutating call
```gherkin
Given an authenticated session with appRole = 'READER'
When it calls any POST, PUT, PATCH, or DELETE endpoint that is not @Public()
Then the response is 403 Forbidden, before the request reaches the controller/service
```

## AC-2: READER keeps full read access
```gherkin
Given an authenticated session with appRole = 'READER'
When it calls a GET endpoint within its own customer scope
Then the response is unaffected (200, same data as before this plan)
```

## AC-3: ADMIN and SYSADMIN are unaffected
```gherkin
Given an authenticated session with appRole = 'ADMIN', or a SYSADMIN/TENANT_ADMIN session (appRole null)
When it calls any POST/PUT/PATCH/DELETE endpoint
Then behavior is identical to before this plan (guard never blocks them)
```

## AC-4: Public routes stay reachable
```gherkin
Given no session at all (e.g. POST /auth/login)
When the request hits a route marked @Public()
Then the new guard does not interfere (matches existing SessionAuthGuard/@Public() behavior)
```

  <name>Task 1: Create ReaderBlockGuard</name>
  <files>backend/src/common/guards/reader-block.guard.ts</files>
  <action>
    New `CanActivate` guard, modeled on `CustomerScopeGuard`'s structure (same file location,
    same FastifyRequest-with-session typing):
    - Read `request.session` (set by SessionAuthGuard). If unset, `return true` (no session
      means a @Public() route already let this through — same no-op pattern CustomerScopeGuard
      uses, don't duplicate the @Public() check here).
    - If `request.method` is one of `POST`/`PUT`/`PATCH`/`DELETE` AND `session.appRole ===
      'READER'`, throw `ForbiddenException('Read-only account — this action is not permitted')`.
    - Otherwise `return true`.
    - GET/HEAD/OPTIONS are never blocked, regardless of role.
    - Do NOT check `session.authority` here — ADMIN/READER are both CUSTOMER_USER at the TB
      authority level; only `appRole` distinguishes them. SYSADMIN/TENANT_ADMIN sessions have
      `appRole: null`, so the `=== 'READER'` check already excludes them without a separate
      bypass branch (avoid adding one — it would be dead code).
  </action>
  <verify>`npx tsc --noEmit` in backend/ passes with the new file</verify>
