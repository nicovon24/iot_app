<objective>
## Goal
A sysadmin can impersonate any Customer User from `/users` ("Login as"), see the app exactly as that user would (their `customerId`/`appRole` scoping applies immediately), and return to their own session with one click. Every impersonation is logged (who, whom, start, end) in a new Postgres table.

## Purpose
Closes the impersonation requirement from Phase 9.2's CONTEXT.md. Depends on 9.2-02 because the "Login as" action lives on the `/users` page that plan builds — there is nowhere else in the app a sysadmin picks a target user from.

Per this session's explicit decision: no live kill-switch (a sysadmin cannot forcibly end someone else's in-progress impersonation session) — ending is always "Back to my session" on the impersonating browser itself, plus normal session TTL expiry. This is a deliberate scope cut, not an oversight.

## Output
- New `ImpersonationLog` Prisma model + migration
- `POST /users/:id/impersonate` (sysadmin-only) — mints a new session for the target user, logs the start
- `POST /users/impersonate/:logId/end` (sysadmin-only) — marks the log's `endedAt`
- Frontend: session-swap helpers, a persistent "Viewing as {email}" banner, "Back to my session" action, "Login as" button per user row on `/users`
</objective>

<acceptance_criteria>

## AC-1: Login as
```gherkin
Given a sysadmin on /users viewing a Customer User row
When they click "Login as" on that row
Then the app immediately reflects that user's session (their customerId/appRole scoping applies to subsequent requests) and a persistent banner reading "Viewing as {email}" appears
```

## AC-2: Back to my session
```gherkin
Given an active impersonation banner is showing
When the sysadmin clicks "Back to my session"
Then the app returns to the sysadmin's own original session without a new login, and the banner disappears
```

## AC-3: Audit trail
```gherkin
Given a completed impersonation (a Login-as followed by a Back-to-my-session)
Then a Postgres ImpersonationLog row exists with the sysadmin's tbUserId as impersonatorId, the target's tbUserId as targetUserId, a startedAt timestamp, and a non-null endedAt timestamp
```

## AC-4: Impersonation endpoints stay sysadmin-only
```gherkin
Given a non-sysadmin session
When it calls POST /users/:id/impersonate or POST /users/impersonate/:logId/end directly
Then it receives 403 (the existing RolesGuard/@Roles('SYSADMIN') on UsersController already covers new routes added to that controller — verify it wasn't accidentally bypassed)
```

<boundaries>

## DO NOT CHANGE
- `backend/src/common/guards/roles.guard.ts` — reuse the existing `@Roles('SYSADMIN')` mechanism as-is, don't add a parallel one
- `frontend/src/lib/api-client.ts` — the request/response chokepoint stays as-is; impersonation only changes WHICH token is sent, never how requests are made

## SCOPE LIMITS
- **No live kill-switch** — a sysadmin cannot forcibly end another active impersonation session from elsewhere; this is an explicit, deliberate scope cut made this session, not a gap to silently fill later without discussion
- **No shorter TTL for impersonated sessions** — they use the same `SESSION_TTL_SECONDS` as a normal login, per explicit decision
- Impersonated sessions reuse the impersonator's own `tbToken`/`tbRefreshToken` rather than a second real TB login for the target — consistent with the existing architecture where entity-scoped TB calls never actually use the caller's own token today (see STATE.md Blockers/Concerns); do not attempt a second TB login as part of this plan
- No general audit-logging system — `ImpersonationLog` is narrowly scoped to impersonation only, per PROJECT.md's existing "Audit Logs" deferred item

</boundaries>
