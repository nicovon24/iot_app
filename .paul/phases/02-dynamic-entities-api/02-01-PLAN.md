<objective>
## Goal
Any Device or Asset can be looked up generically (`GET /entities`), and any attribute or telemetry key it has can be read (`GET /entities/:id/attributes`, `GET /entities/:id/telemetry/...`) — without hardcoding a key set per device type. Reads are Redis-cached with a short TTL.

## Purpose
This is the core PROJECT.md value: an API "far more capable and flexible" than ThingsBoard's native UI, by exposing ThingsBoard's own dynamic entity/key model instead of a fixed schema. It's also the foundation Phase 3 (WS gateways) and Phase 6 (frontend entity views) build directly on top of.

## Output
- `backend/src/entities/` — `EntityRef` type unifying Device/Asset, list + get-by-id
- `backend/src/devices/`, `backend/src/assets/` — thin listing controllers over `entities/`
- `backend/src/attributes/` — scope-based dynamic attribute reads
- `backend/src/telemetry/` — REST: keys / latest / timeseries, string-serialized per `docs/rules/api.md`
- Redis read-through cache wrapper reused across attributes + telemetry
</objective>

<acceptance_criteria>

## AC-1: Generic entity listing
```gherkin
Given ThingsBoard has both Device and Asset entities for the tenant
When a client calls GET /entities?type=DEVICE
Then only devices are returned, normalized to the shared EntityRef shape (id, type, name)
```

## AC-2: Dynamic attributes, any scope
```gherkin
Given an entity has attributes in CLIENT_SCOPE, SERVER_SCOPE, and SHARED_SCOPE
When a client calls GET /entities/:id/attributes?scope=SERVER_SCOPE
Then only that scope's key/value pairs are returned, whatever keys they are — no hardcoded key list in the backend
```

## AC-3: Telemetry contract compliance
```gherkin
Given an entity has a telemetry key "temperature" with decimals=2 in the future telemetry_definitions catalog (not yet built)
When a client calls GET /entities/:id/telemetry/latest
Then each value is serialized as a JSON string (never a JS number), per docs/rules/api.md
```

## AC-4: Redis cache reduces ThingsBoard load
```gherkin
Given GET /entities/:id/telemetry/latest was just called
When the same request is repeated within the cache TTL
Then the second call is served from Redis and does not re-hit ThingsBoard
```

</acceptance_criteria>

  </action>

<task type="auto">
  <name>Task 3: Telemetry REST module (keys/latest/timeseries) with string serialization + Redis cache</name>
  <files>backend/src/telemetry/telemetry.module.ts, backend/src/telemetry/telemetry.controller.ts, backend/src/telemetry/telemetry.service.ts, backend/src/common/dto/telemetry-value.dto.ts</files>
  <action>
    - `telemetry.service.ts`:
      - `getKeys(entityId, entityType)` → TB `/api/plugins/telemetry/{entityType}/{entityId}/keys/timeseries`
      - `getLatest(entityId, entityType, keys?)` → TB `.../values/timeseries` (all keys if `keys` omitted — dynamic, no fixed list), returns `TbTimeseriesLatest`
      - `getTimeseries(entityId, entityType, keys, startTs, endTs, agg?)` → TB `.../values/timeseries?keys=...&startTs=...&endTs=...`
    - `telemetry-value.dto.ts`: response shape `{ value: string; ts: number; decimals?: number }` — `value` is ALWAYS `String(rawValue)`, never returned as a JS number, per `docs/rules/api.md`. `decimals` is `undefined` for now (no `telemetry_definitions` catalog yet — that's a later phase); document this gap in the Swagger description rather than faking a value.
    - Cache read-through on `getLatest` only (short TTL ~3-5s) via `latest:{entityType}:{entityId}` in Redis, keyed by the sorted `keys` list; `getTimeseries` and `getKeys` are not cached (historical/metadata queries, lower frequency)
    - `telemetry.controller.ts`: `GET /entities/:id/telemetry/keys`, `GET /entities/:id/telemetry/latest`, `GET /entities/:id/telemetry/timeseries` — all `@ApiTags('telemetry')`, fully documented in Swagger including the string-serialization contract in each endpoint's description
    - Wire `EntitiesModule`, `DevicesModule`, `AssetsModule`, `AttributesModule`, `TelemetryModule` into `app.module.ts`
    Avoid: recomputing aggregates backend-side — timeseries aggregation (avg/min/max) is out of scope for V1's REST layer; if `agg` param is passed, forward it to TB's own aggregation API, never compute it locally (per `docs/rules/api.md`).
  </action>
  <verify>Swagger `GET /entities/:id/telemetry/latest` returns values as JSON strings; calling it twice within ~5s shows (via added debug log or Redis MONITOR) that the second call is cache-served</verify>
