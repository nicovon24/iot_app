<objective>
## Goal
From `/assets`, a user can open an "Add Asset" flow, pick an existing Client (Customer), choose which hierarchy level the new Asset represents and its parent (the Customer itself for level 0, or an existing Asset for deeper levels), and create a real Asset in ThingsBoard linked via a real "Contains" relation — using the backend already built in Phase 4.3.

## Purpose
Closes the second half of the user's explicit request this session: "poder crear un customer con su jerarquia... y ademas tambien quiero poder crear sus diferentes activos" (Devices explicitly excluded — no backend support exists for Device creation/linking, confirmed and deferred to V2). This reuses `POST /assets` exactly as built in Phase 4.3, no backend changes.

## Output
- `frontend/src/hooks/useCustomerHierarchy.ts`: `useCustomerHierarchy(customerId)` — reads `GET /customers/:id/hierarchy`
- `frontend/src/hooks/useCreateAsset.ts`: `useCreateAsset()` mutation wrapping `POST /assets`
- `frontend/src/types/asset.ts`: `CreateAssetRequest` type mirroring the backend DTO
- `frontend/src/widgets/AddAssetModal.tsx`: the Add-Asset form (Customer → level → parent → name/type/label)
- `frontend/src/app/assets/page.tsx`: gains an "Add Asset" entry point opening the modal
</objective>

## AC-1: Add Asset entry point is discoverable
```gherkin
Given the user is on /assets
When the page loads
Then an "Add Asset" action is visible (button, matching the visual weight of /clients's "Create Client" action from Plan 07-01), opening the AddAssetModal on click
```

## AC-2: Customer + level + parent selection is constrained to real data
```gherkin
Given real Clients (Customers) exist, each with a real hierarchy
When the user picks a Customer in the modal
Then the level dropdown is populated from that Customer's real GET /customers/:id/hierarchy (ordered by levelIndex), and the parent selector offers: the Customer itself (only valid for level 0) or existing real Assets already under that Customer (fetched via GET /assets, client-filtered by customerId) for level 1+
```

## AC-3: Submit creates a real linked Asset
```gherkin
Given a valid selection (Customer, level, parent, name, type)
When the user submits
Then a real POST /assets request is sent with { name, type, label?, customerId, levelIndex, parentId }, and on success the modal closes and /assets' list refetches to show the new Asset
```

## AC-4: Validation errors surface clearly
```gherkin
Given an invalid combination (e.g. level/parent mismatch the backend rejects, or the session lacks permission)
When submit is attempted
Then the real backend error message is shown inline in the modal (via the existing ApiError shape), the modal stays open, and no silent failure occurs
```
