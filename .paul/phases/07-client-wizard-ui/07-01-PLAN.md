<objective>
## Goal
A sysadmin can see all Clients (ThingsBoard Customers) in a list, and create a new one through a 3-step wizard (basic info, ordered hierarchy levels, review) that submits atomically to the existing `POST /customers` backend, with hierarchy immutability made explicit before submit.

## Purpose
Phase 4 already built the backend (`POST /customers`, sysadmin-only, atomic Customer + Postgres hierarchy). The "Clients" nav item has existed since Phase 5 as a `comingSoon` placeholder. This plan makes it real, closing the last gap in V1's core requirement: "Client creation wizard... the only wizard in V1."

## Output
- `frontend/src/hooks/useCustomers.ts`: `useCustomers()` (list), `useCreateCustomer()` (mutation)
- `frontend/src/types/customer.ts`: `HierarchyLevel`, `CreateCustomerRequest` types mirroring the backend DTO
- `frontend/src/app/clients/page.tsx`: real Clients list (replaces `comingSoon`)
- `frontend/src/app/clients/new/page.tsx` + `frontend/src/widgets/ClientWizard.tsx`: the 3-step creation wizard
- `frontend/src/lib/nav-items.ts`: "Clients" nav item flips `comingSoon: false`
</objective>

<acceptance_criteria>

## AC-1: Clients list shows real Customers
```gherkin
Given one or more real Customers exist in ThingsBoard
When /clients loads
Then it shows a real list of Customers (name, type, customer reference) using the same EntityListWidget pattern as /devices and /assets, with a "Create Client" action visible
```

## AC-2: Wizard collects basic info and an ordered hierarchy
```gherkin
Given the user is on /clients/new
When they fill in a Client name and define hierarchy levels (pre-filled with the suggested Site → Area → Asset → Sensor default, editable: add/remove/reorder/rename)
Then the form validates hierarchy is non-empty before allowing progression to review, matching backend's `ArrayMinSize(1)` requirement
```

## AC-3: Review step makes immutability explicit
```gherkin
Given the user has filled in Client info and hierarchy
When they reach the review step
Then it shows a plain-language note that hierarchy cannot be edited after creation, plus a summary of the name and ordered levels, before allowing submit
```

## AC-4: Submit creates a real Customer + hierarchy
```gherkin
Given valid wizard data on the review step
When the user submits
Then a real POST /customers request is sent (name + hierarchyLevels, parentCustomerId omitted for a top-level Client), and on success the user is redirected to /clients showing the new Customer in the list
```

## AC-5: Backend errors surface clearly
```gherkin
Given the submitting session is not sysadmin (403) or hierarchyLevels is somehow empty (400)
When submit is attempted
Then the wizard shows the real backend error message inline (via the existing ApiError shape) instead of a silent failure or a generic crash
```

Do not invent a fake client-side role check.
