<objective>
## Goal
The entity detail page's Alarms and Map tabs (placeholders since 06-02) show real data: Alarms lists an entity's alarms with live push updates; Map renders a pin only when the entity actually has `latitude`/`longitude` telemetry keys (per PROJECT.md's "Map view when available"), otherwise the tab is hidden/disabled rather than shown empty. `/alarms` becomes a real global, filterable alarm list replacing its `ComingSoon` placeholder. This closes Phase 6.

## Purpose
Completes the "drill into any entity" promise from the Phase 6 goal — an operator can now see live alarms and, for entities that report location (the reference pump/station profile per ARCHITECTURE.md does), where they physically are. The global Alarms page is the first cross-entity view in the app, giving an at-a-glance operational picture instead of requiring per-entity drilling.

## Output
- `frontend/src/hooks/useEntityAlarms.ts` (REST, per-entity), `useLiveAlarms.ts` (WS `/ws/alarms` wrapper, same pattern as `useLiveTelemetry`)
- `frontend/src/widgets/AlarmsListWidget.tsx`, `frontend/src/widgets/MapWidget.tsx` (react-leaflet)
- `frontend/src/app/entities/[id]/page.tsx`: Alarms tab wired live; Map tab conditionally shown based on real telemetry keys
- `frontend/src/app/alarms/page.tsx`: real global alarm list (severity/status filters), replacing `ComingSoon`
- `react-leaflet` + `leaflet` added as frontend dependencies
</objective>

## AC-1: Alarms tab shows real per-entity alarm data with live updates
```gherkin
Given a real Device id with alarm history (per STATE.md, real alarms have been created/cleared against ThingsBoard during Phase 3 verification)
When the Alarms tab is open
Then it shows real alarms from GET /entities/:id/alarms (raw TB shape: severity, status, originator, startTs, etc. per frontend/src/types/alarm.ts), and a newly-pushed alarm frame from /ws/alarms updates the list without a manual refresh
```

## AC-2: Map tab only appears when the entity has real location telemetry
```gherkin
Given an entity whose telemetry keys (from 06-02's useKeys()) include both "latitude" and "longitude"
When the entity detail page loads
Then the Map tab is enabled and shows a pin at the real coordinates (parsed from the latest telemetry values); for an entity missing either key, the Map tab is disabled/hidden instead of rendering an empty map
```

## AC-3: Global Alarms page lists and filters alarms across entities
```gherkin
Given the caller's customer-hierarchy-scoped alarm set (GET /alarms, per Phase 2.2 scoping)
When /alarms is loaded, and severity/status filters are applied
Then the list reflects the real scoped data and updates when a filter changes (re-fetch with the new query params), with a clean empty state if the filtered set is empty
```

## AC-4: Alarms live push doesn't leak subscriptions across tab/page navigation
```gherkin
Given the Alarms tab (entity-scoped) or the global Alarms page (both use /ws/alarms) has been open and then navigated away from
When the user returns or opens a different entity's Alarms tab
Then only one active /ws/alarms subscription exists at a time — the prior one was cleanly closed, matching the leak-prevention pattern established for telemetry in 06-02's useLiveTelemetry
```

    `useEntityAlarms(id, type)`: TanStack `useQuery` on `GET /entities/:id/alarms`, query key `['alarms', 'entity', id]`, returns the raw `TbPageData&lt;Alarm&gt;`-shaped response typed via `frontend/src/types/alarm.ts`'s `Alarm`.

  </action>
