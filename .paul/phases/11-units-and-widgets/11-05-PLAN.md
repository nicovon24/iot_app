<objective>
## Goal
A new `label` widget type: free-form static text on a dashboard, no entity/telemetry binding at all — the first widget type with `entity: 'none'`.

## Purpose
Every dashboard widget today assumes an entity. Section headers, instructions, or notes on a dashboard currently have nowhere to go. This is the smallest widget in the phase but exercises a code path (`entity: 'none'` in the config panel) that exists in the code today but has never actually been reached by any real widget type — this plan is the first thing to prove it works, not assume it does.

## Output
- New widget type `label`: `{ text: string, align?: 'left' | 'center' }` config, no datasource fields at all
- `frontend/src/widgets/charts/LabelWidget.tsx`: renders `text` as plain, line-break-preserving text (React's default escaping makes this XSS-safe with zero extra code — no markdown, no `dangerouslySetInnerHTML`, no new dependency)
- Gallery category: grouped under `Cards` (not a new one-item category)
</objective>

<acceptance_criteria>

## AC-1: Label widget has no datasource, backend rejects an entityId if one is somehow sent
```gherkin
Given the label widget's Zod schema
When a config like { entityId: '...', text: 'hello' } is submitted
Then validation rejects it — the schema for 'label' has no entityId/entityScope/entityType
  fields at all (unlike optionalDatasource(), which would silently accept and ignore an
  entityId), because this widget structurally cannot use one and accepting it would be a
  confusing dead field

Given a config { text: 'Section: Pumps', align: 'center' }
Then it validates successfully
```

## AC-2: Config panel shows a text input, not the "no configuration" placeholder or a datasource picker
```gherkin
Given the Add Widget panel with 'label' selected
When the Configure step opens
Then it shows a textarea for the label text (and an alignment choice) — NOT the generic
  "This widget needs no further configuration" placeholder that meta.entity === 'none' has always
  shown for lack of any type actually using it before this plan
```

## AC-3: Renders as plain, safe text
```gherkin
Given a label widget with text containing a line break and the literal string
  "<script>alert(1)</script>"
When it renders on a dashboard
Then the line break is preserved visually (via CSS white-space, not an HTML <br> injected into
  the string) and the script text renders as literal visible characters, never executes —
  React's default JSX text-node escaping is the entire mechanism, no sanitizer library needed
```
