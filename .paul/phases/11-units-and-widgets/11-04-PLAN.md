<objective>
## Goal
Multi-key widgets (`value-cards`, `timeseries-table`) can show a different unit per telemetry key instead of one unit for the whole widget, and a genuinely new widget type — a multi-key comparison chart — lets one entity's several telemetry keys plot together on one chart, with a second Y-axis when the keys resolve to different units.

## Purpose
This is the real gap the earlier plans in this phase don't close: today nothing lets a user plot temperature against pressure for the same pump on one chart. It's also why multi-key units matter here specifically — two keys with different units on one chart is meaningless without knowing which axis is which.

## Output
- `units?: Record<string, string>` config field on `value-cards`, `timeseries-table`, and the new chart type — one unit string per telemetry key
- New widget type `multi-key-chart` ("Comparison Chart"): required single entity, 2-8 telemetry keys, dual Y-axis grouped by resolved unit symbol, third+ distinct unit groups reported via the existing `omittedCount` convention rather than a third axis
- `frontend/src/lib/group-keys-by-unit.ts`: the pure grouping function behind the dual-axis logic, with its own assert-based check (the one genuinely branchy piece of this plan)
</objective>

## AC-1: Per-key units render on value-cards and timeseries-table
```gherkin
Given a value-cards widget configured with telemetryKeys: ['temperature', 'pressure'] and
  units: { temperature: '°C', pressure: 'bar' }
When it renders
Then each entity's card shows "24.6 °C" for temperature and "1.2 bar" for pressure — the correct
  unit per measure, not one unit applied to both

Given a timeseries-table widget with the same keys/units
When it renders
Then the unit appears in each key's column header (not repeated on every cell/row — 20 rows of
  "°C" would be noise)
```

## AC-2: New multi-key-chart widget type exists end-to-end
```gherkin
Given the widget gallery
When browsing the Charts category
Then "Comparison Chart" appears as a new gallery entry with a live preview (not a static icon)

Given a Comparison Chart widget configured with one entity, telemetryKeys: ['temperature',
  'pressure'], units: { temperature: '°C', pressure: 'bar' }
When it renders
Then it draws two lines (one per key) on one chart, with temperature on a left Y-axis labeled
  °C and pressure on a right Y-axis labeled bar

Given the same widget but both keys resolve to the SAME unit (e.g. two temperature keys, both °C)
When it renders
Then both lines share a single Y-axis labeled °C — no redundant second axis for the same unit
```

## AC-3: Three or more distinct units degrade gracefully, never crash or invent a third axis
```gherkin
Given a Comparison Chart with 3 keys resolving to 3 distinct units (e.g. °C, bar, dBm)
When it renders
Then it draws the first 2 unit groups on left/right axes and reports the omitted key via the
  existing omittedCount pattern (e.g. "1 key not shown") — it does NOT render a third axis and
  does NOT silently normalize values onto one axis (which would strip the unit meaning that is
  the whole point of this widget)
```

## AC-4: Entity scope is single-entity only, capped at 8 keys
```gherkin
Given the Comparison Chart's registry entry
Then supportsAllScope is false — N entities × M keys was explicitly rejected as unreadable in
  the phase design, and entity is required (not optional/none)

Given a user tries to select more than 8 telemetry keys for one Comparison Chart
Then the picker/schema rejects it (max(8), matching MAX_SERIES from the existing chart-palette)
```
