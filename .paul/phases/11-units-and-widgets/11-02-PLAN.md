<objective>
## Goal
The widget config panel's unit field becomes a catalog-backed picker (grouped by category, e.g. "Temperature: °C, °F") with a "Custom…" escape hatch that reveals the old free-text input, shown for every widget type that renders a telemetry value (not just the 3 SCALE_TYPES + 2 UNIT_ONLY_TYPES it's hardcoded to today). Selecting a telemetry key auto-suggests a unit unless the user has already set one manually.

## Purpose
Plan 11-01 made `unit`/`decimals` a real field on every widget type, but the only way to set it is still typing free text into an `<Input maxLength={12}>` shown on 5 of 17 types. This plan is what makes the new field actually usable and discoverable — reusing `units.ts`'s catalog (11-01) and `suggestUnit` so most users never type a unit manually at all.

## Output
- `frontend/src/dashboards/widget-config/UnitPicker.tsx`: a new picker component, catalog options grouped by category + a "Custom…" option
- `frontend/src/components/ui/Select.tsx`: `SelectOption` gains an optional `group?: string`, rendered via a Radix `Select.Group`/`Select.Label` when present
- The unit field shows for every widget whose registry entry has `telemetryKey !== 'none'`, not the current hardcoded `UNIT_ONLY_TYPES`/`SCALE_TYPES` unit-input duplication
- `SCALE_TYPES` de-duplicated: exported once from `widget-config/widget-registry.tsx`, imported by both `ConfigureStep.tsx` and `AddWidgetPanel/index.tsx` instead of being declared literally in both files
- Selecting a telemetry key pre-fills the unit via `suggestUnit`, but only if the user hasn't already touched the unit field for this widget
- A `decimals` number input next to the unit picker
</objective>

## AC-1: Unit picker replaces free-text input, offers catalog + custom
```gherkin
Given the config panel for a value-tile widget bound to a telemetry key
When the user opens the Unit field
Then they see catalog units grouped by category (Temperature, Percentage, Signal, ...) plus a
  "Custom…" option at the end

Given the user selects "Custom…"
Then a text input appears where they can type any string up to 24 characters, matching the
  backend's presentation.unit max length from plan 11-01
```

## AC-2: Unit field now available on every value-rendering widget type, not just 5
```gherkin
Given a widget type whose registry entry has telemetryKey !== 'none' (e.g. line-chart, which had
  no unit input before this plan)
When the user opens its config step
Then the unit picker is shown

Given a widget type with telemetryKey === 'none' (e.g. map, alarms-list, donut)
When the user opens its config step
Then no unit picker is shown — unit is meaningless there even though the backend schema now
  technically accepts it (11-01 added it to the shared fragment for schema simplicity, not because
  every type should expose it in the UI)
```

## AC-3: Auto-suggestion doesn't clobber a deliberate choice
```gherkin
Given a new widget, the user picks telemetry key "temperature"
Then the unit field auto-fills "°C" (via suggestUnit)

Given the user then manually changes the unit to "K" (Kelvin, typed via Custom…)
And then changes the telemetry key to a different key
Then the unit stays "K" — it does not get overwritten by the new key's suggestion

Given an existing saved widget with unit "dBm" is opened for editing
Then the picker recognizes "dBm" as a catalog entry (not Custom mode), and changing the telemetry
  key does NOT trigger auto-suggestion (editing an existing widget should never silently rewrite a
  saved value)
```

## AC-4: Back-compat — free-text units saved before this plan open correctly
```gherkin
Given a widget saved with unit: 'widgets/hr' (a free-text value the old <Input> allowed, not in
  the catalog)
When its config step is opened for editing
Then the picker shows "Custom…" selected with "widgets/hr" in the revealed text input — not blank,
  not an error
```
