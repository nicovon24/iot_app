<objective>
## Goal
Every one of the 17 dashboard widget types can carry a real `unit`/`decimals` on its config (today only 5 types can), and every place that renders a formatted number goes through one shared formatter instead of the two duplicates that exist today (`formatTelemetryValue` in `frontend/src/lib/format.ts` and `formatValue` in `frontend/src/widgets/charts/chart-shared.ts`).

## Purpose
This is the foundation the rest of Phase 11 builds on (config-panel picker, multi-key units, the comparison chart). Fixing the formatter here is also the direct payoff: line/bar/scatter charts start showing units in their tooltips and axis labels with zero widget-specific code, because they already call the shared formatter — they just weren't passed a unit before.

## Output
- `frontend/src/lib/units.ts`: a frontend-only unit catalog (categories → `{symbol, label, decimals}[]`), with `resolveUnit(stored)` (known symbol/id → catalog entry, unknown string → passed through as a literal suffix, `undefined` → `undefined`) and `suggestUnit(telemetryKey)` (key-name heuristics, e.g. `temperature`→`°C`, `battery`→`%`, `rssi`→`dBm`)
- `unit`/`decimals` added to the shared `presentation` fragment in the backend widget registry — all 17 widget types accept them, not just the 5 that had a per-type `unit` field
- `formatTelemetryValue` in `frontend/src/lib/format.ts` takes an options object (`{unit?, decimals?}`) instead of a positional `maxDecimals` number; `chart-shared.ts`'s duplicate `formatValue` is deleted and replaced by two thin wrappers (`axisTick`, `withUnit`) built on the shared formatter
- Line/bar/scatter charts render a unit in their tooltip/axis label when the widget's config has one
</objective>

  <name>Task 1: Create the unit catalog module + its self-check</name>
  <files>frontend/src/lib/units.ts, frontend/src/lib/units.check.ts</files>
  <action>
    Create `frontend/src/lib/units.ts`:
    - `export interface CatalogUnit { symbol: string; label: string; decimals: number }`
    - `export const UNIT_CATEGORIES: Record<string, { label: string; units: CatalogUnit[] }>` covering:
      temperature (°C, °F), percentage (%), signal (dBm), pressure (bar, psi, Pa), energy (kWh, J),
      power (W, kW), flow (L/min, m³/h), volume (L, m³), length (m, cm, mm, km), mass (kg, g, t),
      speed (km/h, m/s), duration (s, min, h), count (a dimensionless "count"/"units" entry).
      Each unit gets a sensible default `decimals` (e.g. 1 for °C/°F, 0 for %/dBm/count, 2 for
      pressure/energy). Do NOT add `factor`/`offset`/`baseUnit` fields — no consumer needs them
      without a conversion feature, which is explicitly out of scope for this phase (see
      CONTEXT.md's "Pendiente para más adelante"). Adding unused conversion constants now means
      ~30 untested numbers nobody verifies.
    - `export function resolveUnit(stored?: string): { symbol: string; decimals?: number } | undefined`
      — flatten UNIT_CATEGORIES into a symbol→entry lookup once at module load (a plain object,
      not a Map — this is looked up on every render of every value-carrying widget). If `stored`
      matches a catalog symbol, return `{symbol: stored, decimals: entry.decimals}`. If `stored` is
      a non-empty string not in the catalog, return `{symbol: stored, decimals: undefined}` (the
      back-compat passthrough — old free-text units like 'widgets/hr' must never be dropped or
      throw). If `stored` is undefined/empty, return undefined.
    - `export function suggestUnit(telemetryKey: string): string | undefined` — case-insensitive
      substring match against a small ordered list of heuristics: keys containing 'temp'→'°C',
      'humid'→'%', 'batt'→'%', 'rssi'/'signal'→'dBm', 'pressure'→'bar', 'flow'→'L/min',
      'power'→'W', 'energy'→'kWh', 'speed'/'velocity'→'km/h'. No match → undefined. This
      generalizes the two hardcoded lookup tables already in the codebase (`DIAL_DEFAULTS` in
      renderer/CardCells.tsx and `SCALE_PLACEHOLDERS` in widget-config/AddWidgetPanel/ConfigureStep.tsx)
      without touching either yet — that wiring happens in plan 11-02.
    - Add a one-line comment near the top: aggregations that don't compose under a future unit
      conversion (SUM/COUNT combined with an offset-based unit like °C/°F) are a known trap for
      whenever conversion is added — not a concern for this plan, which never converts a value.

    Create `frontend/src/lib/units.check.ts` following the existing assert-based self-check
    convention (see frontend/src/lib/format.check.ts for the exact style/header-comment pattern —
    run with `npx tsx src/lib/units.check.ts`, no test framework). Assert:
    - every symbol across all UNIT_CATEGORIES is unique (build a Set, compare length) — this is
      the one thing that would silently corrupt the picker in plan 11-02 if violated
    - `resolveUnit('°C')` returns a defined entry with `symbol === '°C'`
    - `resolveUnit('widgets/hr')` returns `{symbol: 'widgets/hr', decimals: undefined}` (unknown
      passthrough)
    - `resolveUnit(undefined)` and `resolveUnit('')` both return `undefined`
    - `suggestUnit('batteryLevel') === '%'`, `suggestUnit('outsideTemperature') === '°C'`,
      `suggestUnit('unknownKey123')` is `undefined`
  </action>
